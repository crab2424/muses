# muses — ステージUI プロトタイプ

`memory/muses-stage-ui-design.md` で確定したステージUI設計を Three.js + TypeScript で実装したもの。
目的は**実機（iPad）での見え方と操作感を確認すること**であり、ゲームとしての完成度ではない。

## ビルド / 起動

```bash
npm install
```

開発サーバ（これが基本。iPad から実機確認するのもこれ）:

```bash
npm run dev
```

Mac 上では `http://localhost:5173`、**同じ Wi-Fi 上の iPad からは `http://192.168.1.23:5173`**
（IP が変わったら `ipconfig getifaddr en0` で確認）。`vite.config.ts` で `host: true` にしてあるので LAN 公開済み。

本番ビルド（型チェック込み）と、そのプレビュー:

```bash
npm run build
```

```bash
npm run preview
```

iPad では Safari で開いて「ホーム画面に追加」するとフルスクリーンになり、
Safari の UI バーによる画面高さの変動がなくなる（NDC 基準の設計なので画面高が変わると全体がずれる）。

## 使い方

- 「TAP TO START」で開始（Web Audio の起動にユーザー操作が必要なため）。
- 右上の **stage params** パネルで全パラメータをリアルタイム調整できる。
  - 「スクリーン空間 (NDC)」= 設計上の正の値。ここを動かすと 3D 側が自動で追従する。
  - 「導出値・実測値」は読み取り専用。fps / 入力イベント Hz / audio latency もここに出る。
  - 「JSON をコピー」で調整後の値をクリップボードへ。
- コンソールから `__muses` で `cfg` / `derived` / `chart` / `input` / `judge` を覗ける。

### パラメータの考え方（2026-07-26 改訂）

**ワールド単位のパラメータをユーザーに触らせない**方針に変えた。以前は「描画最遠」と
「スクロール速度」をワールド単位で指定していたため、画角 φ やカメラ高さ yCam を変えると
それらの意味が変わってしまい、「カメラの項目をどれをいじっても描画最遠の挙動にしかならない」
状態になっていた。現在は:

| 指定するもの | 何が導出されるか |
|---|---|
| `最遠端` (NDC v) | ステージ最遠端の**画面上の位置**。両層の最遠端が画面上の同じ行に来る |
| `先読み時間` (秒) | ノーツが最遠端から判定線まで来る時間。ワールド速度はここから逆算 |

これで φ・yCam を変えても最遠端の見た目と先読み時間は動かない。
`カメラ高さ yCam` は**純粋なスケール**で、投影像は完全に不変（そういう項目だと明示してある）。
`垂直画角 φ` だけが遠近の付き方（奥行きの圧縮カーブ）を変える。

## 実装が設計メモに対応している箇所

| 設計メモの項目 | 実装 |
|---|---|
| 画面上の y 座標 = 視線の向き、`ψ(v) = θ − atan(v·tan(φ/2))`、`d = (y_cam − y_p)/tan ψ` | [derive.ts](src/derive.ts) |
| スクリーン空間の権威値（地平線 0.75 / 空中判定線 0.35 / y_split −0.10 / 地上判定線 −0.57 など） | [config.ts](src/config.ts) |
| 判定線 `z_j` は層に依らない単一の奥行き。判定帯の厚みはタイミングと無関係 | [derive.ts](src/derive.ts)、[judge.ts](src/judge.ts) |
| 判定帯はワールド空間のポリゴンではなく**スクリーン空間のオーバーレイ** | [overlay.ts](src/overlay.ts)（2D canvas） |
| `layer = (v > y_split) ? 1 : 0`、`cell = clamp(floor((u+U)·n/(2U)), 0, n−1)`、押下中はヒステリシス | [input.ts](src/input.ts) |
| セル境界は垂直（消失点へ収束させない） | [overlay.ts](src/overlay.ts) |
| レーン境界はワールドの x 一定の直線 → 画面上では消失点に収束 | [stage.ts](src/stage.ts) |
| `(layer, cell)` の座標方式アドレッシング | 全体 |
| 層間遷移中の追従型判定（ノーツが占めるセルが逐次アクティブ） | [judge.ts](src/judge.ts) の arc 処理 |
| セル数の細分化は 12 → 24/36 に変えるだけ | パネルの「セル数」 |
| アスペクト比対応（垂直画角固定、横幅は NDC 比率固定、ワールド幅のみ再計算） | [derive.ts](src/derive.ts) |

デフォルト値での導出結果は設計メモの表と一致することを確認済み
（θ=19.28°, z_j=14.74, h=7.40, 地上幅 17.98 / 1セル 1.50, 空中幅 15.43 / 1セル 1.29,
地上帯の奥行き幅 6.55 に対し空中帯 16.23, 地上の可視限界 38.73）。

## 未設計のまま暫定実装した部分

設計メモで「未着手」とされていた項目。**確認の際はここが仮であることに注意**。

- **判定ウィンドウ / スコアリング**: PERFECT 45ms / GOOD 100ms、コンボのみ。ライフ・スコア計算式なし。
- **ノーツ種別**: タップ / ロング / アーク（層間遷移）の 3 種だけ。
- **譜面フォーマット**: [chart.ts](src/chart.ts) にデモ譜面を手続き的に生成しているだけで、外部フォーマットは未定義。
- **ロングノーツの失敗条件**: 保持が 0.2 秒外れたら break、終点は離してよい（メモの記述に合わせた）。
- **アークの判定開始**: 接触トリガではなく開始時刻に自動で追従判定へ入る方式。
- **楽曲**: なし。メトロノーム（パネルで ON）のみ。

## 幾何から出た重要な帰結: 両層の先読み時間は独立に選べない

両層が同じワールド速度で動く場合、先読み時間の比は次の式に**固定される**:

```
空中の先読み / 地上の先読み  =  (y_cam − h) / y_cam  =  tan ψ(空中判定線) / tan ψ(地上判定線)
```

つまり**2本の判定線の画面上の位置だけで比が決まる**。最遠端をどこに置いても、速度を何にしても変わらない。
空中判定線を画面上部へ持っていくほど空中の先読みは短くなる。

- 現在の既定値（空中 42.5% / 地上 78%）: 地上 1.80 秒に対し **空中 0.49 秒**
- 旧・設計メモの値（空中 32.5% / 地上 78.5%）: 比 0.26 でさらに短い

0.49 秒はほぼ反応不能なので、`両層の先読みを揃える` オプション（既定 ON）を入れた。
これは**層ごとにスクロール速度を変える**もので、判定線の奥行き `z_j` とタイミングは共通のまま、
空中ノーツだけゆっくり近づく。OFF にすると従来どおり同一速度になるので、見比べて選べる。

## 確認してほしい観点

1. **空中の先読み** — 上記のとおり構造的に短い。`両層の先読みを揃える` の ON/OFF を見比べる。
2. **1セルの実寸** — パネルに 11 インチ換算の mm 表示あり。`U` を上げると広がる。
3. **判定帯の垂直セル境界と、床の収束レーンのズレ** — 判定線上でのみ一致し、帯の端でずれる。
   実際に見て許容できるか。
4. **iPad Safari の Web Audio 遅延**（パネルの audio latency）、**fps**、**入力イベント Hz**。
   ProMotion 端末で fps と入力 Hz が 120 まで出るかはここで実測する。
