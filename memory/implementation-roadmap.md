## 1. 挙げてもらったリストへの評価

### そのまま最優先でよいもの
- **フリックなどの新ノーツ検討** — ○。ただし後述のとおり**入力層の拡張とセット**であり、
  かつ**データモデルの前**に置くべき（種別が確定しないと 1 ノーツのパラメータが決まらない）。
- **ノーツ判定処理（特にアーク）** — ○。ここが今いちばん「未設計のまま暫定実装」が濃い。
- **譜面エディタ（1 ノーツに必要なパラメータの検討）** — ○だが、
  括弧内（＝パラメータ検討）は上流の設計課題であり、エディタ本体（UI・ツール）は下流。
  **この 2 つは切り離すべき**。

### 依存関係を修正したいもの
- **判定枠（ステージが台形ゆえ）** — ⚠ **この問題は設計上すでに解決済み**。
  判定帯はワールド空間のポリゴンではなく**スクリーン空間のオーバーレイ**で、
  セル境界は垂直・消失点へ収束させない方式に決めてある（`overlay.ts` / `input.ts`）。
  台形のステージでも判定枠は長方形の鍵盤として置かれ、`cell` はタッチの y に依存しない。
  したがって残っている実問題は次の 3 点だけで、いずれも「台形」の話ではない:
  1. `laneConverge = 1`（現行既定）のとき、**描画上の床レーンと入力のセル境界が判定線上でしか一致しない**
     （帯の端で約 1 セルずれる）。`laneConverge` を下げれば連続的に解消できる。**これは見た目の選択**。
  2. **1 セルの実寸（人間工学）**。`U = 0.87` / 12 セルで 11 インチ換算 17.3mm 前後。
     指幅より狭いと隣セル誤爆が出る。実機で詰める項目。
  3. **層をまたいで移動中のアークの判定枠をどう可視化するか**（下の 4-2 参照）。これは未着手。

- **ノーツ UI / ステージ UI** — ○だが、**「視認性の最低限」と「演出」を分けて**、
  前者だけ先に上げるべき。今の色設計では層の区別も前後関係も弱く、
  **判定を詰める作業そのものが「見えない」せいで成立しない**。逆にヒットエフェクト等の
  演出は判定仕様が固まってからでよい。

## 2. 抜けている項目（重要な順）

### A. 譜面データフォーマット（時間軸の単位を含む）— **最大の抜け**
「譜面エディタ」の括弧内に含まれているようにも読めるが、独立した設計項目として立てるべき。
`chart.ts` は今、秒で直接ノーツを生成しているだけで、シリアライズ形式が存在しない。
決めるべきこと:
- **時間軸の単位**: 秒 か、**拍/tick（BPM とオフセットから秒へ変換）**か。
  → 音ゲーはほぼ例外なく後者。BPM 変化・小節線・スナップ（1/4, 1/6, 1/8…）が全部これに乗る。
  **後から秒→拍へ移行するのは既存譜面の作り直しを伴うので、ここは今決める。**
- **座標の単位**: `cell`（整数）と `cellF`（連続値）が今は混在。tap/hold は整数セル、
  arc は連続値という現状の分岐を保つか、全部連続値に寄せて描画時だけ量子化するか。
- ファイル形式（JSON でよい）、バージョン番号フィールド（**初手で入れる**。後付けは面倒）。
- 曲メタ（BPM、オフセット、難易度、曲長）とノーツ列の分離。

これが決まらないとエディタは書けず、判定のテストも書けない。**エディタより先。**

### B. タイミング基盤（オフセット / キャリブレーション）
`audio.ts` は `outputLatency` を表示するだけで、**判定に反映していない**。必要なもの:
- `judgeOffset`（音と入力のズレ補正）と `visualOffset`（音と描画のズレ補正）の**2 系統**。
- プレイヤー向けキャリブレーション画面（後回しでよいが、**開発中の自分用スライダは今すぐ要る**）。
- 楽曲再生への移行（現在はメトロノームのみ）。判定を詰めるには実際の曲が要る。
  権利の要らない曲 1 本（自作 or CC0）を早めに置く。

### C. 実機計測 → プラットフォーム最終判断
`muses-platform-decisions.md` に「iPad Safari の Web Audio 遅延と fps を実測し、
60fps を割るなら Unity へ切り替える」という**段階判断が未決のまま残っている**。
判定処理・エディタ・見た目を作り込んでから Unity へ移すのは損失が大きい。
**判定を本設計する前にここを閉じる。** 測るもの: audio latency / fps / 入力イベント Hz
（3 つとも既に画面に出ている）＋ノーツ密度を上げた最悪ケース。

### D. シーク（任意時刻へのジャンプ）
エディタに**必須**。「この小節から再生」ができないとエディタは使い物にならない。
今の `Judge` は `cursor` を単調増加させる前提なので、**任意時刻へ飛ぶと壊れる**。
「`songTime` を与えたら全ノーツの state を再構築できる」形にしておく必要がある。
実装コストは小さいが、**後から入れると判定コードを書き直すことになる**ので、
判定を本実装するときに同時に設計へ入れる。

### E. 判定フィードバック（エフェクト＋音）
判定の善し悪しは「当たった感触」でしか評価できない。ヒットエフェクト、
判定文字、**早い/遅い表示**（判定窓の調整に直結するので開発中こそ要る）、ヒット音。
「ノーツ UI」の一部として扱ってよいが、**早い/遅い表示だけは判定作業のために先に**。

### F. ポーズ / リトライ / 即時リスタート
「その他モードの画面遷移」に含めて後回しにされがちだが、**リトライは開発効率に直結**する
（1 箇所の判定を確認するのに毎回頭から聴き直すのは非現実的）。D と一緒に入れる。

### G. 設定の永続化
今は GUI で調整 → JSON を手動コピー → `settings.json` に貼る運用。
localStorage への自動保存＋プリセット切替（明背景/暗背景など）にしておくと実機調整が速くなる。小コスト。

### H. 判定ロジックのテスト
時刻と入力を注入できれば `Judge` は純粋関数的にテストできる。
フリック・アークの条件分岐が増えると手動確認が破綻するので、
**判定を本実装するタイミングで最小限のテスト土台を入れる**。

### I. 曲・権利・デプロイ
草案に項目だけある未着手枠。C の判断が済むまで動かせないので保留でよいが、
**デモ用の楽曲 1 本**は B のために早めに要る。

## 3. 推奨する実装順

各フェーズは「前のフェーズが決まらないと手戻りする」順に並べてある。
フェーズ内の項目は並行してよい。

### Phase 0: リスクを閉じる（短期・最優先）
> 目的: 後の全作業の前提を確定させる。作り込む前に判断する。

1. **実機計測**（項目 C）。iPad で audio latency / fps / 入力 Hz を実測。
   ノーツ密度を意図的に上げた譜面でも 60fps（できれば 120）を維持できるか。
2. **Three.js 継続 / Unity 移行の判断**を明文化して閉じる。
3. **オフセット 2 系統を config に追加**（項目 B の最小版）。GUI にスライダを出すだけ。
4. **設定の localStorage 保存**（項目 G）。以降の実機調整が全部速くなる。

### Phase 1: ゲームの「語彙」を決める（設計フェーズ、コードは最小）
> 目的: 1 ノーツが何を持つかを確定する。ここが動くと下流が全部動く。

5. **ノーツ種別の確定**（＝挙げてもらった「フリックなどの新ノーツ検討」）。→ 詳細は 4-1。
6. **譜面データフォーマットの確定**（項目 A）。5 の結果を型とスキーマに落とす。
   時間軸を拍/tick へ移行し、`chart.ts` のデモ譜面を新フォーマットの JSON として書き出す。
7. **判定仕様の言語化**（種別ごとの成立条件・失敗条件・窓）。コードより先に文章で。→ 4-2。

### Phase 2: 見えるようにする（並行可・短期）
> 目的: 以降の判定調整を「目で評価できる」状態にする。演出はまだ作らない。

8. **視認性の最低限**: 層の識別（色相を明確に分離）、前後関係（明度・サイズ・フォグ）、
   ステージ面と背景のコントラスト。既に設計メモに結論がある
   （明背景にするなら加算合成→通常合成、ノーツ 2 メッシュ分離＋renderOrder、
   ノーツ色の明度反転が前提条件）。**明背景にするかを先に決める**——決めないと 2 度塗りになる。
9. **早い/遅い表示**（項目 E の一部）と、判定内訳の HUD。

### Phase 3: 判定を本実装する（本丸）
> 目的: 暫定実装を仕様に置き換える。

10. **入力層の拡張**: 接触ごとの速度・移動履歴の保持（フリックの前提）、
    アーク追従中の指を tap 判定から除外する仕組み。→ 4-3。
11. **判定処理の本実装**: tap / hold / arc / 新種別。**シーク対応（項目 D）を同時に設計へ入れる**。
12. **ポーズ・リトライ**（項目 F）。
13. **判定ロジックのテスト土台**（項目 H）。
14. **判定枠の残課題**: `laneConverge` の最終決定、1 セル実寸の実機調整、
    層間遷移中のアークの判定枠可視化。

### Phase 4: 譜面エディタ
> 目的: 譜面を「書ける」ようにする。Phase 1 の 6 が済んでいれば素直に作れる。

15. タイムライン UI（小節・拍・スナップ）、ステージプレビュー上での配置、
    再生/シーク、undo、JSON 入出力。→ 4-4。

### Phase 5: ゲームとして閉じる（後回し宣言どおり）
16. スコアリング、クリア条件、ライフ、リザルト、曲選択、画面遷移、楽曲設定・譜面設定。
    **ただし判定内訳（PERFECT/GOOD/MISS の分類）は Phase 3 で確定している必要がある**
    ——スコア式はその上に載るだけなので後回しでよいが、分類自体は後回しにできない。

## 4. 各テーマの検討ポイント

### 4-1. 新ノーツ種別（フリック等）の検討軸

**本作固有の制約**: コアコンセプトは「タップではなく、入力範囲に新規の接触が現れたら判定」＝
**プレイヤーに特定の操作を要求しない**方向の設計。一方フリックは「特定の方向へ弾く」という
**要求を増やす**方向で、原理的に緊張関係にある。導入するなら「なぜこの緊張を許容するか」を先に決める。

候補と評価:

| 候補 | 内容 | 実装コスト | 本作との相性 |
|---|---|---|---|
| **層跨ぎフリック** | `vSplit` を跨いで指を弾く。地上⇄空中の縦移動 | 中（既存の layer 遷移で検出可） | **◎ 本作固有**。2 層構造を活かす唯一の種別 |
| **セル間スライド** | 隣接セルへ指を移動。既存の `cell` 更新イベントでほぼ表現できる | **小** | ○ 既存の入力モデルの延長。ほぼ無料 |
| 方向フリック（左右） | 指定方向へ一定速度以上で弾く | 中（速度履歴が要る） | △ arc / スライドと役割が被る |
| 同時押し（複数セル） | 指定セル群を同時に占有 | 小（`isOccupied` の AND） | ○ 12 セルの 2 層＝24 セルを活かせる |
| ホールド中の移動要求 | hold の中継点で横移動を要求（草案の「中継点で変形」の強化版） | 小（arc の一種として表現可） | ◎ **草案に既にある**。arc と統合できる |

**推奨**: まず「層跨ぎフリック」と「セル間スライド」を検討。どちらも既存の入力モデルの
自然な拡張で、方向フリックのように新しい入力概念（速度閾値）を持ち込まない。
方向フリックは、その 2 つを試して**まだ表現の幅が足りないと感じたら**足す。

**種別を増やす前に確認すること**: 現状の tap/hold/arc で、そもそも「表現したい譜面」が
書けないのか。エディタ（Phase 4）がない今、arc の表現力は実は未検証。
デモ譜面を手で数パターン書いて、足りない語彙を実感してから決めるほうが確実。

### 4-2. 判定処理の未決事項（コードから洗い出したもの）

**アーク**:
- **開始トリガ**: 現在は開始時刻に達すると接触なしで自動的に `active` になる（`judge.ts`）。
  つまり**アークは開始を「取り逃す」ことが原理的にできない**。ノーツとして成立していない。
  決めるべき: 始点で接触を要求するか / 要求するならその窓は tap と同じか。
- **追従を外れた時の grace**: 現在 0.2 秒固定。arc は指の移動を要求するので、
  tap/hold と同じ値でよいのかは要検証。
- **層間遷移とヒステリシスの干渉**: 指の layer は `splitHysteresis`（0.05）で遅れて切り替わるが、
  ノーツ側は `layerF > 0.5` で二値化している。境界付近で両者がずれる期間が生じる。
  grace 0.2 秒で吸収されている可能性が高いが、**アークがゆっくり層を跨ぐ譜面で必ず検証**すること。
- **判定枠の可視化**: 層を移動中のアークは、判定帯オーバーレイのどこがアクティブなのかが
  プレイヤーに見えない。追従型判定は「なぞる操作と一致する」前提だが、
  その前提はアークの帯が判定帯の上に投影されて初めて成り立つ。
- **アーク幅とセル量子化**: `cellRange` が `floor`/`ceil` で実質 1〜2 セル広く取っている。
  `width` の意味（見た目の幅 = 判定の幅か）を決める。

**tap との相互作用（潜在的な誤爆）**:
- アークを追従中の指がセルを跨ぐと `input.emit()` が発火し、`Judge.onEnter` に届く。
  そのため**アークをなぞっている指が、近くの tap を勝手に取ってしまう**可能性がある。
  仕様として許すのか（同時押しの緩和）、禁止するのか（追従中の指は tap 判定から除外）を決める。

**tap / hold**:
- 判定窓（PERFECT 45ms / GOOD 100ms）は暫定値。実機の入力 Hz とレイテンシ実測後に決める。
- hold の終点は「離す必要なし」＝草案どおり。失敗条件 0.2 秒は暫定。
- **同時刻・同セルに複数ノーツがある場合**の解決規則（1 接触で何個取れるか）が未定義。

### 4-3. 入力層に足りないもの

- 接触ごとの**速度・移動履歴**（フリック導入時の前提。今は現在位置のみ）。
- **アーク追従中フラグ**（4-2 の誤爆対策）。
- 多点上限とパームリジェクション（実機で問題が出てから）。
- **`fresh` フラグの使い分け**: `EnterEvent.fresh`（新規接触 か セル移動か）は
  今 `Judge` で使われていない。「タップしなくても取れる」仕様の核心なので、
  種別ごとにどちらを要求するか（tap は両方 OK、フリックは移動のみ、等）を明示する。

### 4-4. 1 ノーツに必要なパラメータ（エディタ設計の入口）

現在の型（`chart.ts`）を出発点に、確定すべき項目:

共通:
- `kind` / `time`（→ 拍 or tick へ移行）/ `layer` / `cell` / `width`
- `id`（エディタの選択・undo・差分に必要。**今は無い**）

種別ごと:
- hold: `endTime`、**中継点**（草案の「中継点を駆使して変形可」は**まだ未実装**。
  現状の `HoldNote` は始点と終点だけ。arc に中継点があるので、
  **hold を arc の特殊形として統合するか**は設計判断のポイント）
- arc: `points[]`（`time` / `layerF` / `cellF`）、補間方式（現在 smoothstep 固定 →
  **点ごとに指定可能にするか**。Arcaea 系は s/si/so 等を持つ）、`width`
- 新種別: 方向、速度閾値など

譜面全体:
- BPM（変化リスト）、オフセット、小節構成（拍子）、難易度、曲情報、フォーマットバージョン

## 6. まとめ: 挙げてもらった 6 項目の配置

| 挙げてもらった項目 | 推奨フェーズ | 補足 |
|---|---|---|
| フリックなどの新ノーツ検討 | **Phase 1** | 入力層拡張とセット。まず既存 3 種の表現力不足を実感してから |
| ノーツ UI | Phase 2（視認性）→ Phase 5（演出） | 分割する |
| ステージ UI | **Phase 2** | 明背景にするかを先に決める（前提条件が連鎖する） |
| ノーツ判定処理（特にアーク） | **Phase 3** | シーク対応を同時に設計へ入れる。未決事項は 4-2 |
| 判定枠 | Phase 3（残課題のみ） | **台形問題は設計上すでに解決済み**。残るは laneConverge・実寸・アーク可視化 |
| 譜面エディタ | パラメータ検討 = **Phase 1** / ツール本体 = **Phase 4** | 切り離す |

**追加すべき最重要 3 項目**:
1. **実機計測 → プラットフォーム最終判断**（Phase 0）— 作り込む前に閉じる
2. **譜面データフォーマットと時間軸の単位**（Phase 1）— エディタの前提。後から変えると譜面を作り直す
3. **オフセット / タイミング基盤**（Phase 0-1）— 判定を詰める前提
