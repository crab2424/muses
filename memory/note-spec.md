# muses ノーツ仕様（Phase 1 / 2026-07-31 改訂 rev.2）

対象: **Tap / Slide / Flick** の3種と、Slide に付く**中継点**。
目的は「今あるものを確定させる」ことに加えて、**今後ノーツ種別が増えても
データモデル・描画・判定のどれも作り直さずに済む形にする**こと。

関連: `implementation-roadmap.md`（Phase 1 の位置づけ）、`unity-stage-port-design.md`（ステージ座標系）。

> rev.2 の主な変更: 旧 Hold と旧 Arc を **Slide に統合**。判定解像度・幅・easing・
> Flick 成立条件・tick 単位・縦連判定を確定。「拘束済み接触点の除外」は不採用に変更。

## 0. 前提となる座標系・入力モデル

- ステージは **地上(Ground)** と **空中(Sky)** の2層。層は `layer ∈ {0,1}`、
  連続値で扱う場合は `layerF ∈ [0,1]`。
- 横方向は `cells` 個（現行 12）のセルに等分割。整数セル `cell`、連続値は `cellF`。
- 入力は NDC `(u, v)` から離散化される（`TouchInputManager`）:
  - `layer = (v > vSplit) ? Sky : Ground`（押下中の指のみ `splitHysteresis` を適用）
  - `cell = clamp(floor((u + U) * cells / (2U)), 0, cells-1)`
- 判定トリガは「入力範囲内に新規接触、またはセル/層をまたぐ移動が発生した」＝ `EnterEvent`。
  以降これを **「枠内更新」** と呼ぶ。

### 0.1 入力パネルの内部バンド分割（擦り対応）

各層を画面の上下方向（v 軸）に **`bandsPerLayer` 個（既定 2）** のバンドへ内部分割し、
入力の最小単位を **`(layer, cell, band)`** にする。**バンド境界をまたいだだけでも
同じセルに対する枠内更新が発生する**ため、指を上下に小刻みに動かすことで
同一セル上で連続的な入力更新が得られる（＝縦連を「擦り」で処理できる）。

- 判定側は band を無視する（ノーツは層内の全バンドを占有しているものとして扱う）。
  band は**枠内更新を発生させるためだけ**に存在する。
- 参考: CHUNITHM の地上スライダーが 16列 × 2行 = 32センサーなのと同じ構造。
- 分割数は実機で決める（`bandsPerLayer` を設定値として持つ）。

### 0.2 判定解像度は種別ごとに異なる

| 種別 | 解像度 | 駆動 |
|---|---|---|
| **Tap** | **離散**（`(layer, cell, band)` の更新イベント） | イベント駆動 |
| **Slide** | **連続座標**（`(cellF, layerF)` の距離） | 占有駆動 |
| **Flick** | **連続座標** + 移動量 | 占有 + 移動 |

Tap だけ離散なのは、§0.1 の擦りが**更新イベント**を必要とするため。
Slide / Flick を連続にする理由:

- 上下（層）方向の厳しさを `width` と判定半径で連続的に調整できる
- `splitHysteresis` と `layerF > 0.5` 二値化のずれが消える（旧 Arc の既知問題）
- 幅 1〜12 セルの連続値を自然に扱える
- **計算量でも不利にならない**（下記）

計算量の見積もり（接触4点・同時進行 Slide 3本・cells=12、1フレームあたり）:

| | 内訳 | 概算 |
|---|---|---|
| 離散セル | Slide ごとに最大12回の HashSet 探索 → 36回 | 約 0.7 µs |
| 連続座標 | 接触ごとの逆変換4回 + Slide ごとに 4接触×箱判定 | 約 0.05 µs |

離散は「幅の分だけセルを舐める」が、連続は「接触点の数だけ」で済む。
接触点は多くても4〜5本なので、幅12セルの Slide でも比較回数は増えない。

**連続座標への逆変換**: `cellF` は `u` の線形写像。`layerF` は判定線の奥行き `zJudge`
における地上/空中の画面 `v`（`StageDerive` から算出）を用いて
`layerF = (v - vGround) / (vSky - vGround)` の線形逆変換。毎フレーム接触点ごとに数命令。

## 1. 共通データモデル（拡張性の核）

種別ごとにクラスを増やすのではなく、**「形状」と「判定の性質」を分離**し、
種別は両者の組み合わせのプリセットとして定義する。新種別の追加は
プリセット表に1行足すだけで、描画・判定の分岐は増えない。

### 1.1 形状: すべてのノーツは「Waypoint の列」

```
Note {
  kind        : NoteKind        // Tap / Slide / Flick / …（プリセットの選択）
  points      : Waypoint[]      // Tap/Flick は1個、Slide は2個以上
}

Waypoint {
  tick        : int             // 譜面先頭からの累積 tick（§5）
  layerF      : float           // 0=地上 … 1=空中（連続値）
  cellF       : float           // セル境界インデックスの連続値
  width       : float           // この点における帯の幅（セル数）
  easing      : Easing          // 「この点から次の点まで」の補間種別。既定 Linear
  marker      : WaypointMarker  // None / Visible / Invisible（§3）
  comboStep   : int?            // この点から次の点までのコンボ刻み幅の上書き（§2.3）。null なら自動
}
```

- **Tap / Flick** は `points.Length == 1` の退化形。幅は始点の `width`。
- **Slide** は `points.Length >= 2`。始点 = `points[0]`、終点 = `points[^1]`、
  間にあるものがすべて**中継点**。
- 幅を点ごとに持たせることで「始点・中継点・終点で幅を変更可能」を満たす。
  区間内の幅は `easing` に従って補間する。
- **幅はデータ上 float**。エディタ側で 0.5 / 1.0 セル刻みにスナップする。
  連続判定なら float の実装コストがゼロ（箱判定の閾値が float になるだけ）で、
  描画側は既に float 幅を扱えるため、後から刻みを緩めるのも締めるのも自由。
  Tap は離散判定なので、エディタでは整数セルにスナップする運用とする。

### 1.2 補間（直線 / 曲線）

`easing` は**列挙型に限定する**（任意の数式を許すとフォーマット・エディタ・判定が
際限なく複雑になるため）。初期セット:

| 値 | 内容 |
|---|---|
| **`Linear`（既定）** | 直線 |
| `Smooth` | smoothstep (`k*k*(3-2k)`)。旧 `ChartMath.ArcAt` の挙動 |
| `SineIn` / `SineOut` / `SineInOut` | sin 曲線 |
| `QuadIn` / `QuadOut` | 2次関数 |

- 補間は `layerF` / `cellF` / `width` すべてに同じ easing を適用する（当面）。
  別々に指定したくなったら `easing` を構造体に昇格させれば拡張できる。
- **現行 `ChartMath.ArcAt` は smoothstep 固定**なので、Linear 既定への変更が入る。

### 1.3 判定の性質（トレイト）

種別ごとの振る舞いを、直交する属性の組で表す。

| 属性 | 値 | 意味 |
|---|---|---|
| `startTrigger` | `Contact` / `Auto` / `Presence` | 始点の成立条件 |
| `sustain` | `None` / `Ticks` | 開始後、刻みごとの継続判定を行うか |
| `motion` | `None` / `Flick` | 追加で入力の**移動**を要求するか |
| `resolution` | `Cell` / `Continuous` | §0.2 の判定解像度 |

### 1.4 種別プリセット

| kind | points | startTrigger | sustain | motion | resolution |
|---|---|---|---|---|---|
| **Tap**   | 1  | `Contact` | None | None | **Cell** |
| **Slide** | ≥2 | `Contact` | **Ticks** | None | **Continuous** |
| **Flick** | 1  | `Presence` | None | **Flick** | **Continuous** |

**新種別を足す手順**: `NoteKind` に値を足し、この表に1行足し、必要なら
見た目用のパラメータ構造体を足す。判定側は属性を見て動くので `switch` は増えない。

## 2. Slide（旧 Hold + 旧 Arc の統合）

旧 Hold と旧 Arc はデータ構造が完全共通で、違いは判定解像度だけだった。
**統合して Slide 1種にする**ことで、区別のための概念が丸ごと消え、
種別が Tap / Slide / Flick の3つになる（理解負荷の低減が主目的）。

- **操作は「なぞる」**。「押さえ続ける」はこれに包含される
  （全 Waypoint が同じ位置の Slide ＝ 旧 Hold）。
- **層は連続値**（`layerF ∈ [0,1]`）を取り、層をまたぐ軌跡を書ける。
- **幅は 1〜12 セルの任意の値**（データは float、エディタでスナップ）。
- **判定解像度は連続座標**（§0.2）。

### 2.1 判定モデル: 「等間隔に並んだ判定点の列 + 見た目の帯」

Slide は全体を1つの状態機械で扱わない。**コンボ点（判定点）を独立に判定する**。

- 各コンボ点の時刻に、いずれかの接触点が Slide の帯の内側にあれば成立。
- **一度逃して MISS になっても、途中から押し直せば残りのコンボ点は成立する。**
- これにより旧実装の「HOLD BREAK（0.2 秒離れたら丸ごと失敗）」という状態機械が消える。
- **始点のコンボ点のみ枠内更新（`Contact`）を要求**し、以降のコンボ点は
  「その時刻に枠内に入力が存在するか」だけを見る。

**帰結**: 総ノーツ数（＝理論値）が Slide の長さに依存する（意図どおり）。
難度表記・スコア計算式はこれを前提にする。

### 2.2 コンボ点の生成規則

コンボ点は **Waypoint 区間ごとに生成**する。

```
コンボ点集合 =
    { Slide 始点 }
  ∪ { Slide 終点 }
  ∪ { Visible 中継点 }                                    // §3
  ∪ { 各区間 [W_i, W_{i+1}] で、W_i から comboStep 刻みで進んだ点
      （W_i 自身は除く／区間終端を超えない範囲） }
（時刻が重複するものは1つに統合）
```

- **Invisible 中継点はコンボ点にならない**（区間の分割にのみ使う）。
  自動生成が区間始点自身を打たないのはこのため。
- 区間長が `comboStep` で割り切れない端数は、次の区間の始点で吸収する
  （端数のコンボ点は打たない）。

### 2.3 コンボ刻み幅（`comboStep`）の決定

**規則: 刻みの実時間が 0.125〜0.25 秒（毎秒 4〜8 コンボ）に収まる音価を選ぶ。**

| BPM 帯 | 音価 | 刻みの実時間 | tick 数（`ticksPerBeat=5040`） |
|---|---|---|---|
| 30〜59 | 32分 | 0.250 → 0.127s | 630 |
| **60〜119** | **16分** | 0.250 → 0.126s | **1260** |
| **120〜239** | **8分** | 0.250 → 0.126s | **2520** |
| **240〜479** | **4分** | 0.250 → 0.126s | **5040** |
| 480〜959 | 2分 | 0.250 → 0.125s | 10080 |

太字がユーザー指定分。境界の 60 / 120 / 240 は上記の帯の切れ目そのものなので、
規則を実時間で持てば表外の BPM も自動で決まる。

- **BPM が変化する場合、その境界時刻に中継点を置くことを必須とする。**
  刻み幅は区間単位で決まるので、区間の途中で BPM が変わることは許さない。
  置かれていない場合は**エディタ側で警告を出す**。
- `Waypoint.comboStep` による**上書きを許可**する（null なら上記表から自動決定）。
  BPM 119 と 120 で刻みが倍違うため、境界付近の曲で作者の意図と異なる方を
  引く可能性があるのを救う。

## 3. 中継点（Slide 専用）

`Waypoint.marker` で表現する。

| marker | 見た目 | コンボ / スコア |
|---|---|---|
| `Visible`（**ノーツ型**） | Tap と同じ形・**別色** | **あり** |
| `Invisible`（**無形型**） | 描かない | なし |
| `None` | 描かない（純粋な形状制御点） | なし。将来用に予約 |

- Visible 中継点も **枠内更新は不要**（Tap と違い、押し直す必要はない）。
  §2.1 のコンボ点として「その時刻に枠内に入力があるか」だけで判定される。
- 中継点同士の直線/曲線描画は §1.2 の `easing` が担う。
- 幅の変更は `Waypoint.width` が担う。

## 4. Flick

**判定方式は「座標移動」**（接触点の NDC 座標の移動量を見る）。
セル更新の複数回検出は**不採用**——セル境界のすぐ横で始めたフリックは 1px で成立し、
セル中央で始めたフリックはセル幅の半分動かないと成立しない、という
**成否の位置依存**が音ゲーとして致命的なため。

### 4.1 成立条件

**「枠内に接触点が存在」かつ「直近 `flickWindowMs` の移動量が `flickDistance` 以上」**。

- **新規接触は不要**。既に動いている指が枠内を擦り抜けても成立する
  （`startTrigger = Presence`）。**本質は枠内の移動**であって、接触の開始ではない。
- 成立タイミングは**移動量が閾値を超えた瞬間**の時刻。この時刻で判定窓を評価する。
- 実装には `Contact` に「直近 `flickWindowMs` 分の `(u, v, time)` リングバッファ」が要る。

### 4.2 パラメータ（要チューニング、初期値は仮）

| 名前 | 意味 | 仮の初期値 |
|---|---|---|
| `flickDistance` | 成立に必要な NDC 上の移動量 | 0.06 |
| `flickWindowMs` | その移動を行うべき時間窓 | 120 ms |
| `flickDirection` | `Any` / `Left` / `Right` / `Up` / `Down` | **`Any` のみ実装**（他はフィールドのみ予約） |

## 5. 時間軸（tick）

### 5.1 確定事項

- 譜面上の時刻は **拍ベースの tick**。**`ticksPerBeat = 5040`**（int）。
- tick は**譜面先頭からの累積値**（前のノーツからの差分ではない）。
  差分方式は途中挿入で以降が全部ずれるため採らない。
- 秒への変換: `秒 = tick / ticksPerBeat × (60 / BPM)`。
  BPM 変化には `bpmEvents: (tick, bpm)[]` を持ち、
  **譜面ロード時に1回だけ** tick→秒 の変換テーブルを構築する。
- ランタイム（`NoteRuntime` / `NoteGeometry` / 頂点に焼く値）は**秒のまま**。
  変換を譜面フォーマット層に閉じ込め、既存の描画・判定への影響を最小化する。

### 5.2 `ticksPerBeat = 5040` を選んだ理由

- `5040 = 2^4 × 3^2 × 5 × 7`。**1〜10 のすべてで割り切れる**（LCM(1..10)=2520 の性質を維持）。
- **`5040 / 16 = 315` → 64分音符まで整数**。
  2520 だと `2520/16 = 157.5` で 64分音符が表現できない（2 の因数が3つしかない）。
- 3連系も整数: `/12 = 420`、`/24 = 210`、`/48 = 105`。
- 1920 / 960 は 7 で割り切れないため、7連符を使う余地がなくなる。
- コストは無視できる。5分・BPM200 の曲で 1000拍 × 5040 = 504万 tick、
  int32（上限 21億）に十分収まる。変換はロード時1回きり。

### 5.3 なぜ実時間ベース（2520 tick/秒）を採らないか

**音価が整数 tick にならない**ため。譜面フォーマットとして致命的。

```
BPM 130 の8分音符 = 0.230769s × 2520 = 581.538 tick   ← 非整数
BPM 133 の4分音符 = 0.451128s × 2520 = 1136.842 tick  ← 非整数
```

大半の BPM で 4分音符すら整数にならず、丸めれば 16分連打で誤差が累積して曲とずれる。
拍ベースなら音価は BPM に関係なく常に整数（4分 = 5040、8分 = 2520、16分 = 1260、
3連 = 1680、7連 = 720）。加えて:

- エディタで拍にスナップできる（譜面は「16分の3つ目」で置くもので、秒では置かない）
- BPM を後から直したとき譜面全体が自動追従する（実時間ベースだと全打ち直し）
- §2.3 の「BPM で刻み幅を決める」仕様が自然に書ける（8分 = `ticksPerBeat/2`）

### 5.4 「時刻」「表示位置」「スクロール速度」の3層分離（ソフランの受け皿）

| # | 概念 | 何で決まるか | 判定への影響 |
|---|---|---|---|
| 1 | **時刻**（いつ叩くか） | tick + BPM → 秒 | **あり** |
| 2 | **表示位置**（画面のどこに描くか） | 時刻 + スクロール速度 | **なし** |
| 3 | **スクロール速度** | ソフラン等のギミック | **なし** |

現行コードも既にこの分離になっている（位置はデータとして持たず、毎フレーム導出）:

```
depth = zJudge + (noteTime - songTime) * speed
```

**ソフランを入れる場合**、`speed` を定数から `scrollEvents: (tick, 倍率)[]` の積分
`X(t) = ∫ scroll(τ) dτ` に置き換え、

```
depth = zJudge + (X(noteTime) - X(songTime)) * speed
```

とする。実装上は**頂点に焼く値を「時刻」から「表示位置 X(noteTime)」に変え、
uniform を `X(songTime)` にする**だけで済み、**判定には一切触れない**。

> ソフランの詳細仕様は未策定（ユーザーが検討中）。ここは受け皿の位置だけ示している。

## 6. 判定ティアと縦連判定

### 6.1 判定ティア

**ティアは配列データとして持つ**（列挙型 + `switch` にしない）:

```
JudgeTier[] = [ (name, halfWidthMs, scoreWeight, comboBreak) ]
```

こうしておけば、ティアを増やしても §6.2 の縦連判定が自動的に追従する。

- 現状 Perfect(±40ms) / Good(±100ms) / Miss。**Perfect の上にもう1ティア追加予定**。
- 名称・数値・Good のペナルティは判定窓の広さとあわせて**今後検討**（保留）。

### 6.2 縦連判定（中点分割）

**目的**: ノーツ間隔が極端に短いとき、入力の暴発が次のノーツを不利な判定で
食ってしまうのを防ぐ。代償として判定窓が狭くなり MISS は出やすくなる。

**規則**:

```
対象集合 T = { Tap, Flick, Slide の始点 }

ノーツ N ∈ T について、同一 layer かつセル範囲が交差する N' ∈ T のうち、
  prev(N) = t_{N'} < t_N を満たす最近傍
  next(N) = t_{N'} > t_N を満たす最近傍

  loBound(N) = prev があれば (t_prev + t_N) / 2、なければ -∞
  hiBound(N) = next があれば (t_N + t_next) / 2、なければ +∞

  実効窓(N) = [t_N - W_worst, t_N + W_worst] ∩ [loBound(N), hiBound(N)]
```

`W_worst` = 最下位ティア（現状 Good）の半幅。

- **ティアごとの処理は不要。全ティア共通の1本の窓を中点で切るだけ。**
  判定ティアは切った後の窓の中で通常どおり `|dt|` で決まる。
- **Slide の途中コンボ点は対象外**（対象は始点のみ）。
- **層が違えば無関係**（別の手で押す想定）。
- MISS は `songTime` が実効窓の上限を超えた時点で確定する
  （素の窓より早く確定するため、次のノーツを叩く前にフィードバックが返る）。

**効き方の確認**（3連続 0 / 80 / 160ms、Good ±100、Perfect ±40）:

```
A: [-100, +100] ∩ (-∞, +40]   = [-100,  +40]
B: [ -20, +180] ∩ [+40, +120] = [ +40, +120]   ← Perfect 窓と完全に一致
C: [ +60, +260] ∩ [+120,  ∞)  = [+120, +260]
```

**Δ ≤ 2 × windowPerfect（現設定で 80ms）になると Good が構造的に消える**。
BPM 187.5 の16分がちょうどこの境界。

**現行実装との差分**: 現行 `Judge.OnEnter` は既に「候補の中から `|dt|` 最小のノーツを
選ぶ」実装で、中点分割は「入力を時間的に最も近いノーツに帰属させる」ことと数学的に
等価なので、**帰属の部分は実質すでに入っている**。実際に変わるのは次の2点で、
ここが縦連判定の本体:

1. **解決済みノーツの領域に落ちた暴発入力が、次のノーツを食わなくなる。**
   現行は候補を Pending に限るため、A を叩いた直後の暴発が、窓が後ろに伸びている
   B（素の窓 [-20, +180]）に届いて Good で食ってしまう。中点で切れば B は +40 まで
   到達不能になり、暴発はどのノーツにも当たらず無害に落ちる。
2. **MISS の確定タイミングが早まる**（上記）。

**実装**:

- 中点は距離に対して単調なので、**「全ペアを見る」と「前後それぞれの最近傍だけを見る」は
  結果が同一**（B から見て、より遠い D の中点は必ず C の中点より外側にある）。
  よって **前後の最近傍のみ**で実装する。
- 譜面ロード時に **O(n) で precompute**。実行時コストはゼロ。
- 走査の打ち切り条件が「全ノーツ共通の窓」から「ノーツ固有の実効窓」に変わるため、
  現行 `Judge` の `cursor` 走査ロジックに修正が要る。
- **同一層でセル範囲が交差する同時刻ノーツ**（`t_prev == t_N`）は中点が自分自身の時刻に
  なって窓が潰れる。これは譜面上ありえない配置なので、**エディタ側で禁止する**。

### 6.3 Slide 追従中の指による Tap 誤爆について

**除外しない**（rev.1 の「拘束済み接触点の除外」ルールは**不採用に変更**）。

Slide をなぞっている指がセル/バンド境界をまたぐと枠内更新が発生し、通りがかりの
Tap を誤爆しうるが、これは**想定内**とし、**譜面編集のレギュレーションとして縛る**。
§0.1 のバンド分割で更新イベントが増えるぶん、レギュレーション側の負荷は上がる。

> 誤爆回避のための追加仕様はユーザーが別途検討中。
