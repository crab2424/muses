# muses ノーツ仕様（Phase 1 / 2026-07-30 起草）

対象: tap / hold / arc / **flick（新規）** と、hold・arc に付く **中継点**。
目的は「今あるものを確定させる」ことに加えて、**今後ノーツ種別が増えても
データモデル・描画・判定のどれも作り直さずに済む形にする**こと。

関連: `implementation-roadmap.md`（Phase 1 の位置づけ）、`unity-stage-port-design.md`（ステージ座標系）。

---

## 0. 前提となる座標系・入力モデル（既存、確認のみ）

- ステージは **地上(Ground)** と **空中(Sky)** の2層。層は `layer ∈ {0,1}`、
  連続値で扱う場合は `layerF ∈ [0,1]`。
- 横方向は `cells` 個のセルに等分割。整数セル `cell`、連続値は `cellF`（セル境界インデックスの連続値）。
- 入力は NDC `(u, v)` から次で離散化される（`TouchInputManager`）:
  - `layer = (v > vSplit) ? Sky : Ground`（押下中の指のみ `splitHysteresis` を適用）
  - `cell = clamp(floor((u + U) * cells / (2U)), 0, cells-1)`
- 判定のトリガは「**入力範囲内に新規の接触点、またはセル/層をまたぐ移動が発生した**」＝ `EnterEvent`。
  以降この文書ではこれを **「枠内更新」** と呼ぶ（ユーザーの用語に合わせる）。

### 0.1 離散セル判定と連続座標判定（重要な方針）

現状の判定はすべて「セル占有 (`Occupied[layer, cell]`)」ベース。これは tap/hold には合っているが、
arc（および flick）では以下の既知問題を生む:

- arc は `layerF` の連続値を持つのに、判定時に `layerF > 0.5` で二値化している。
  一方入力側は `vSplit ± splitHysteresis` で層を決めるので、**両者の境界がずれる**。
- arc は帯が細い（`width ≈ 1.2 セル`）ため、セル境界にまたがると
  「隣のセルにいるのに当たり判定に入っていない／入っている」が直感と合わない。

**方針**: 判定の解像度をノーツ種別ごとに選べるようにする。

| 判定モード | 使う種別 | 内容 |
|---|---|---|
| `Cell`（離散） | tap / hold | 従来どおり `Occupied[layer, lo..hi]` のいずれかが占有されていれば有効 |
| `Continuous`（連続） | arc / flick | 指の NDC `(u, v)` を `(cellF, layerF)` に連続変換し、ノーツ中心線との距離で判定 |

連続判定にすると、arc の上下判定が「層をまたいだか」ではなく
「帯の中心からどれだけ離れているか」になるため、
**上下判定の厳しさは `width`（帯の太さ）と判定半径で連続的に調整できる**ようになり、
`splitHysteresis` との不整合も消える。
ロードマップにあった「入力パネルの上下内部分割」は、この連続判定を採れば不要
（＝分割ではなく座標を使う、が推奨）。

`layerF` の連続化には、入力の `v` から
`layerF = clamp((v - vGroundCenter) / (vSkyCenter - vGroundCenter), 0, 1)` のような
逆変換が要る。地上/空中それぞれの画面上の中心 `v` は `StageDerive` から求められるので実装可能。

## 1. 共通データモデル（拡張性の核）

ノーツ種別ごとにクラスを増やすのではなく、**「形状」と「判定の性質」を分離**し、
種別は両者の組み合わせのプリセットとして定義する。新しい種別を足すときは
プリセット表に1行足すだけで、描画・判定の分岐は増えない。

### 1.1 形状: すべてのノーツは「制御点の列」

```
Note {
  kind        : NoteKind        // Tap / Hold / Arc / Flick / …（プリセットの選択）
  points      : Waypoint[]      // 1個以上。tap/flick は1個、hold/arc は2個以上
  // 種別ごとの追加パラメータは kind に応じた小さな構造体で持つ（例: flick の direction）
}

Waypoint {
  time        : Tick            // 拍/tick（後述 §5）
  layerF      : float           // 0=地上 … 1=空中（連続値）
  cellF       : float           // セル境界インデックスの連続値
  width       : float           // この点における帯の幅（セル数、小数可）
  easing      : Easing          // 「この点から次の点まで」の補間種別
  marker      : WaypointMarker  // None / Visible / Invisible（中継点の見た目、§3）
}
```

- **tap** は `points.Length == 1` の退化形。**幅は始点の `width`**。
- **hold / arc** は `points.Length >= 2`。始点=`points[0]`、終点=`points[^1]`、
  間にあるものがすべて **中継点**。
- 幅を点ごとに持たせることで「始点・中継点・終点で幅を変更可能」という要求を満たす。
  区間内の幅は `easing` に従って補間する。

### 1.2 補間（直線 / 曲線）

`easing` は**列挙型に限定する**。任意の数式を許すと譜面フォーマット・エディタ・
判定の全部が際限なく複雑になるため。初期セット:

| 値 | 内容 |
|---|---|
| `Linear` | 直線 |
| `Smooth` | smoothstep（`k*k*(3-2k)`）。**現行 `ChartMath.ArcAt` の挙動がこれ** |
| `SineIn` / `SineOut` / `SineInOut` | sin 曲線 |
| `QuadIn` / `QuadOut` | 2次関数 |

- 補間は `layerF` / `cellF` / `width` の**すべてに同じ easing を適用**する（当面）。
  別々に指定したくなったら `easing` を構造体に昇格させれば拡張できる。
- 現行実装は全区間 `Smooth` 固定なので、`Linear` を既定にするか `Smooth` を既定にするかは
  移行時に決める（**推奨: `Linear` を既定**。エディタで置いた点の通りに動くほうが直感的で、
  曲線は明示的に選ぶ）。

### 1.3 判定の性質（トレイト）

種別ごとの振る舞いを、以下の直交する属性の組で表す。

| 属性 | 値 | 意味 |
|---|---|---|
| `startTrigger` | `Contact` / `Auto` | 始点で枠内更新が必要か、時刻到達で自動成立か |
| `hold` | `None` / `Occupancy` | 開始後、継続して入力がノーツ内に存在する必要があるか |
| `motion` | `None` / `Flick` | 追加で入力の**移動**を要求するか |
| `resolution` | `Cell` / `Continuous` | §0.1 の判定解像度 |
| `moves` | `bool` | 時間とともに位置が動くか（＝形状が単点でないか、から導出可） |

### 1.4 種別プリセット

| kind | points | startTrigger | hold | motion | resolution | 備考 |
|---|---|---|---|---|---|---|
| `Tap`   | 1   | Contact | None | None | Cell | 現行どおり |
| `Hold`  | ≥2  | Contact | Occupancy | None | Cell | §2 参照 |
| `Arc`   | ≥2  | Contact | Occupancy | None | Continuous | §2 参照。**現行は `Auto` だが `Contact` へ変更** |
| `Flick` | 1   | Contact | None | Flick | Continuous | §4 参照 |

**新種別を足すときの手順**: `NoteKind` に値を足し、この表に1行足し、
（必要なら）見た目用のパラメータ構造体を足す。判定側は属性を見て動くので `switch` は増えない。

## 2. Hold と Arc の区別

ユーザー要求「両者の違いをはっきりさせたい。hold が3次元移動できても構わない」に対する整理。

両者とも **「始点で枠内更新が発生し、その後 入力がノーツ内に存在する間 有効」** という
判定の骨格は同じ（＝ `startTrigger=Contact`, `hold=Occupancy`）。よって違いは
**「プレイヤーに要求する操作」と「判定解像度」**に置くのが自然:

| | Hold | Arc |
|---|---|---|
| 想定操作 | **押さえ続ける** | **なぞる（追従する）** |
| 位置の変化 | 原則 静止。動く場合もゆっくり・セル単位の移動 | 時間とともに動くことが前提 |
| 層 (`layerF`) | 原則 0 または 1 に固定（2次元＝横×時間） | 0〜1 の連続値を取り、層をまたぐ（3次元） |
| 幅 | 太い（複数セル）。誤差に寛容 | 細い（1セル前後）。追従精度を要求 |
| 判定解像度 | `Cell`（離散セル占有） | `Continuous`（中心線からの距離） |
| 見た目 | セル格子に沿った帯 | 空間を通るリボン |

**採用する定義（提案）**:
> **Hold = 判定がセル格子に量子化されるロングノーツ。Arc = 判定が連続座標のロングノーツ。**

この定義なら「hold が3次元移動する」ことも禁止されない（`layerF` を 0→1 に動かす hold は
書けるが、判定はセル単位に丸められる＝アバウトに取れる）。一方 arc は連続判定なので
細かい軌跡を要求できる。**データ構造は完全に共通**で、違うのは `resolution` と
エディタ／描画のプリセットだけになる。

### 2.1 現行実装からの変更点

- **arc の `startTrigger` を `Auto` → `Contact` に変更**。
  現行 `Judge.Update` は arc の開始時刻に到達したら接触なしで `Active` にしており、
  **arc を取り逃すことが原理的に不可能**というロードマップ既知の問題がある。
  始点で枠内更新を要求すれば tap/hold と同じ枠組みに揃う。
- arc 追従中に指がセルをまたぐと `EnterEvent` が飛び、**近くの tap を誤爆する**問題
  （ロードマップ既知）は、`EnterEvent` に「どの接触点が出したか (`contactId`)」を持たせ、
  **既にいずれかの長押し系ノーツに拘束されている接触点からの `EnterEvent` は
  tap/flick の判定に使わない**、という規則で解消する。

## 3. 中継点（hold / arc 専用）

`Waypoint.marker` で表現する。

| marker | 見た目 | 判定 |
|---|---|---|
| `None` | 何も描かない（純粋な形状制御点） | なし |
| `Visible`（**ノーツ型**） | tap と同じ形・**別色** | なし（更新不要） |
| `Invisible`（**無形型**） | 何も描かない | なし |

- ユーザー指定どおり **ノーツ型も判定を持たない**（tap と違って枠内更新は不要）。
  「見た目でリズムを示す」役割のみ。
- `None` と `Invisible` は実質同義になるので、**当面 `marker` は
  `Visible` / `Invisible` の2値でよい**（`None` は将来「形状だけの点」を
  明示的に区別したくなったときのために予約）。
- **スコア加算するか**は未決。加算するなら `Waypoint.scored : bool` を足す
  （chunithm 系だと中継点は加点対象になることが多い）。
  **推奨: 初期は加点なし**。コンボ数がノーツ数と一致するほうが譜面難度の見積もりが楽。
- 中継点同士の直線/曲線描画は §1.2 の `easing` がそのまま担う。
- 幅の変更も `Waypoint.width` がそのまま担う。

## 4. Flick（新規）

「入力の移動」を判定する。判定方式の2案について:

### 案A: タップ位置の座標移動（**推奨**）
接触点の NDC 座標を毎フレーム記録し、
「一定時間 `flickWindowMs` 以内に、一定距離 `flickDistance` 以上、
（方向指定があればその向きに）移動したか」で成立とする。

- 利点:
  - セル幅・セル境界の位置に依存せず、**どこでフリックしても同じ距離で成立**する。
  - 将来「上下左右のフリック」を入れる場合、上下は層境界が1本しかないので
    セル更新では表現できない。座標なら自然に扱える。
  - 判定閾値が実距離なので、タブレットの画面サイズに合わせた調整がしやすい。
- 欠点: 接触点ごとの短い履歴（直近数フレームの座標）を `Contact` に持たせる必要がある。

### 案B: 入力パネル（判定幅）の複数更新
「同一接触点が短時間に N セル以上またいだ」で成立とする。

- 利点: 既存の `EnterEvent` だけで実装でき、追加の状態がほぼ要らない。
- 欠点: セル境界のすぐ横で始めたフリックは 1px 動かしただけで成立し、
  セル中央で始めたフリックはセル幅の半分動かないと成立しない。
  **同じ操作の成否が位置依存になる**のは音ゲーとして致命的。

→ **案A を採用**する。`Contact` に「直近 `flickWindowMs` 分の `(u, v, time)` リングバッファ」を追加。

### 4.1 パラメータ（要チューニング、初期値は仮）

| 名前 | 意味 | 仮の初期値 |
|---|---|---|
| `flickDistance` | 成立に必要な NDC 上の移動量 | 0.06 |
| `flickWindowMs` | その移動を行うべき時間窓 | 120 ms |
| `flickDirection` | `Any` / `Left` / `Right` / `Up` / `Down` | 当面 `Any` のみ実装 |

- 成立タイミングは「**移動が閾値を超えた瞬間**」の時刻で判定窓（`windowPerfect`/`windowGood`）を評価する。
- 始点の接触自体は tap と同じく枠内更新で捕捉し、そこから移動を待つ。
  「接触なしで通り過ぎる指」でも成立させるかは未決（**推奨: 成立させる**＝
  フリック連打で指を離さず擦る譜面を許す）。

## 5. 時間軸（Phase 1 の残り）

現行はすべて **秒（float）**。Phase 1 の要件どおり **拍/tick** へ移す。

- 譜面ファイル上の時刻は `tick`（整数）。`ticksPerBeat = 480`（一般的な値。
  3連符 160、16分 120 が整数で表せる）。
- BPM 変化に対応するため、譜面は `bpmEvents: (tick, bpm)[]` を持ち、
  `tick → 秒` の変換テーブルを読み込み時に構築する。
- ランタイム（`NoteRuntime` / `NoteGeometry` / 頂点に焼く時刻）は**秒のまま**でよい。
  変換は譜面ロード時に1回だけ行う。
  → 既存の描画・判定コードへの影響を最小化できる。
- **注意**: 変換は「譜面フォーマット層」に閉じ込め、`Note.points[].time` は
  ロード後に秒へ解決済みの値を持つ設計にする（エディタは tick 側を編集する）。

2. 中継点にスコアを与えるか（推奨: 初期は与えない）。
3. easing の既定を `Linear` にするか `Smooth`（現行）にするか。
4. Flick を「接触なしで擦り抜けても成立」にするか。
5. Flick の方向指定（上下左右）を初期実装に含めるか（推奨: `Any` のみで始める）。
6. `ticksPerBeat` を 480 で確定してよいか。
7. 判定ウィンドウ（`windowPerfect` / `windowGood`）は暫定値のまま。
   種別ごとに変える必要があるか（flick は一般に緩め）。
