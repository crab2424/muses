## 0. 前提となる座標系・入力モデル

- ステージは **地上(Ground)** と **空中(Sky)** の2層。層は `layer ∈ {0,1}`、
  連続値で扱う場合は `layerF ∈ [0,1]`。
- 横方向は `cells` 個（現行 12）のセルに等分割。整数セル `cell`、連続値は `cellF`。
- 入力は NDC `(u, v)` から離散化される（`TouchInputManager`）:
  - `layer = (v > vSplit) ? Sky : Ground`（押下中の指のみ `splitHysteresis` を適用）
  - `cell = clamp(floor((u + U) * cells / (2U)), 0, cells-1)`
- 判定トリガは「入力範囲内に新規接触、またはセル/層をまたぐ移動が発生した」＝ `EnterEvent`。
  以降これを **「枠内更新」** と呼ぶ。

### 0.1 入力パネルの内部バンド分割（擦り対応）

各層を画面の上下方向（v 軸）に **`bandsPerLayer = 2`（確定）** のバンドへ内部分割し、
入力の最小単位を **`(layer, cell, band)`** にする。**バンド境界をまたいだだけでも
同じセルに対する枠内更新が発生する**ため、指を上下に小刻みに動かすことで
同一セル上で連続的な入力更新が得られる（＝縦連を「擦り」で処理できる）。

- 判定側は band を無視する（ノーツは層内の全バンドを占有しているものとして扱う）。
  band は**枠内更新を発生させるためだけ**に存在する。
- 参考: CHUNITHM の地上スライダーが 16列 × 2行 = 32センサーなのと同じ構造。

**バンド境界は独立した設定値として持つ**（`vBandGround` / `vBandSky`）。
判定線基準にするか等分にするかは実機で決めるが、どちらも同じ1値で表現できるので
データ構造としてはこれで確定する。現行値での比較:

| 層 | パネル範囲 (NDC v) | 判定線 | 等分の境界 | 判定線基準の分割比 |
|---|---|---|---|---|
| Ground | `-1.0 … -0.1` | `-0.75` | **`-0.55`** | 0.25 : 0.65 |
| Sky | `-0.1 … +1.0` | `+0.15` | **`+0.45`** | 0.25 : 0.85 |

既定は等分（太字）。判定線基準は片側が薄くなり擦りの余地が小さいため、初期値には採らない。

### 0.1.1 層間の共有帯（保留 / 受け皿のみ）

将来 **Tap が中間層に配置される**可能性に備え、「地上と空中の境界付近の帯にいる
1本の指が、両層のパネルに同時に入力を出す」という共有帯を検討していた。

**rev.3 では共有帯そのものは実装しない**（設定値 `vShareLo` / `vShareHi` の受け皿だけ用意し、
既定は幅0＝共有なし）。理由:

- 共有すると1本の指で地上ノーツと空中ノーツを同時に叩けるため、**Tap 誤爆の新しい発生源**になる。
- 回避には「空中優先」等の優先規則が要るが、その規則は**中間層 Tap の仕様が決まらないと確定しない**
  （地上ノーツしか無い場面で共有帯の指が地上を叩けるのか等が未定）。先に作ると作り直しになる。
- 現行の `splitHysteresis = 0.05`（押下中の指は層を変えにくい）が、実用上の近い効果を既に持つ。

### 0.2 「包含判定」と「駆動」を分けて考える

判定は直交する2つの問いに分解できる。**この2つは独立に選べる。**

- **包含判定**: どこに入力があれば「当たり」か（離散セル / 連続座標）
- **駆動**: 何が判定を起こすか（枠内更新 / コンボ点の時刻 / 移動量の閾値超過）

| 種別 | 包含判定 | 駆動 |
|---|---|---|
| **Tap / Ex Tap** | **離散**（`(layer, cell, band)`） | **枠内更新** |
| **Slide 始点** | **連続座標**（`(cellF, layerF)`） | **枠内更新**（Tap と同じ） |
| **Slide 継続コンボ点** | **連続座標** | コンボ点の時刻（占有駆動、§2.4） |
| **Flick** | **連続座標** + 移動量 | 移動量が閾値を超えた瞬間（§4.4 で枠内更新も見る） |

**Slide 始点は「Tap と同じ枠内更新で駆動されるが、包含判定は連続座標」**という組み合わせを取る。

- 枠内更新で駆動されるので、**同時刻の Tap / Ex Tap と同じ入力イベントでまとめて解決される**（§6.4）。
- 包含判定が連続座標なので、**中間層（`layerF ≈ 0.5`）から始まる Slide も書ける**。
  離散にすると始点だけ `layerF > 0.5` の二値化が復活し、`splitHysteresis` とのずれが再発する。
- トレイト（§1.3）としては `startTrigger = Contact` が駆動を、
  `resolution = Continuous` が包含判定を表す。**属性の追加は不要。**

Tap だけ包含判定が離散なのは、§0.1 の擦りが**更新イベント**を必要とするため。
Slide / Flick の包含判定を連続にする理由:

- 上下（層）方向の厳しさを `width` と判定半径で連続的に調整できる
- `splitHysteresis` と `layerF > 0.5` 二値化のずれが消える（旧 Arc の既知問題）
- 幅 1〜12 セルの連続値を自然に扱える
- **計算量でも不利にならない**（下記）

計算量の見積もり（接触4点・同時進行 Slide 3本・cells=12、1フレームあたり）:

| | 内訳 | 概算 |
|---|---|---|
| 離散セル | Slide ごとに最大12回の HashSet 探索 → 36回 | 約 0.7 µs |
| 連続座標 | 接触ごとの逆変換4回 + Slide ごとに 4接触×箱判定 | 約 0.05 µs |

離散は「幅の分だけセルを舐める」が、連続は「接触点の数だけ」で済む。
接触点は多くても4〜5本なので、幅12セルの Slide でも比較回数は増えない。

**連続座標への逆変換**: `cellF` は `u` の線形写像。`layerF` は判定線の奥行き `zJudge`
における地上/空中の画面 `v`（`StageDerive` から算出）を用いて
`layerF = (v - vGround) / (vSky - vGround)` の線形逆変換。毎フレーム接触点ごとに数命令。

## 1. 共通データモデル（拡張性の核）

種別ごとにクラスを増やすのではなく、**「形状」と「判定の性質」を分離**し、
種別は両者の組み合わせのプリセットとして定義する。新種別の追加は
プリセット表に1行足すだけで、描画・判定の分岐は増えない。

### 1.1 形状: すべてのノーツは「Waypoint の列」

```
Note {
  kind        : NoteKind        // Tap / ExTap / Slide / Flick / …（プリセットの選択）
  scrollGroup : int             // スクロールグループ（§5.5）。既定 0
  points      : Waypoint[]      // Tap/ExTap/Flick は1個、Slide は2個以上
}

Waypoint {
  tick        : int             // 譜面先頭からの累積 tick（§5）
  layerF      : float           // 0=地上 … 1=空中（連続値）
  cellF       : float           // 帯の左端（連続値）。右端は cellF + width。全種別で共通の基準（rev.6）
  width       : float           // この点における帯の幅（セル数）
  easing      : Easing          // 「この点から次の点まで」の cellF/width（横方向）の補間種別。既定 Linear
  easingH     : Easing          // 「この点から次の点まで」の layerF（高さ方向）の補間種別。既定 Linear（rev.5）
  marker      : WaypointMarker  // None / Visible / Invisible（§3）
  comboStep   : int?            // この点から次の点までのコンボ刻み幅の上書き（§2.3）。null なら自動
}
```

- **Tap / Ex Tap / Flick** は `points.Length == 1` の退化形。幅は始点の `width`。
- **Slide** は `points.Length >= 2`。始点 = `points[0]`、終点 = `points[^1]`、
  間にあるものがすべて**中継点**。
- 幅を点ごとに持たせることで「始点・中継点・終点で幅を変更可能」を満たす。
  区間内の幅は `easing` に従って補間する（`easingH` ではない。§1.2）。
- **幅はデータ上 float**。エディタ側で 0.5 / 1.0 セル刻みにスナップする。
  連続判定なら float の実装コストがゼロ（箱判定の閾値が float になるだけ）で、
  描画側は既に float 幅を扱えるため、後から刻みを緩めるのも締めるのも自由。
  Tap / Ex Tap は離散判定なので、エディタでは整数セルにスナップする運用とする。
- `scrollGroup` は**ノーツ単位**（Waypoint 単位ではない）。1本の Slide が途中で
  スクロール速度を変えることはない。

### 1.2 補間（直線 / 曲線）

`easing` は**列挙型に限定する**（任意の数式を許すとフォーマット・エディタ・判定が
際限なく複雑になるため）。初期セット:

| 値 | 内容 |
|---|---|
| **`Linear`（既定）** | 直線 |
| `Smooth` | smoothstep (`k*k*(3-2k)`)。旧 `ChartMath.ArcAt` の挙動 |
| `SineIn` / `SineOut` / `SineInOut` | sin 曲線 |
| `QuadIn` / `QuadOut` | 2次関数 |

- **rev.5 で `easing` を横方向専用（`cellF`/`width`）に据え置き、高さ方向（`layerF`）用に
  `easingH` を新設**した。区間の easing は区間開始側 Waypoint の値を使う点は両者共通。
  以前は両方に同じ `easing` を適用していたが、「sky のノーツは高さを変えても
  横位置は変化しない」設計（editor-ui-rework-mmw.md §4）と合わせ、横と高さで
  別カーブを指定できるようにした（editor-ui-rework-r2.md §6）。
- ファイル形式は `ease=` を横用のまま流用し、高さ用に `easeh=` を追加する。
  `easeh=` を省略した既存譜面は `ease=` の値が両軸に流用されるため完全互換。
- **現行 `ChartMath.ArcAt` は smoothstep 固定**なので、Linear 既定への変更が入る。
- この列挙はソフランの補間（§5.5）でも再利用する（ソフランは単一軸なので `easingH` は無関係）。

### 1.3 判定の性質（トレイト）

種別ごとの振る舞いを、直交する属性の組で表す。

| 属性 | 値 | 意味 |
|---|---|---|
| `startTrigger` | `Contact` / `Auto` / `Presence` | 始点の成立条件 |
| `sustain` | `None` / `Ticks` | 開始後、刻みごとの継続判定を行うか |
| `motion` | `None` / `Flick` | 追加で入力の**移動**を要求するか |
| `resolution` | `Cell` / `Continuous` | §0.2 の判定解像度 |
| **`judgeProfile`** | `Normal` / **`AllPerfect`** | 窓内を常に最高ティアにするか（§6.1） |
| **`chainExempt`** | `false` / **`true`** | 自身の窓を縦連の中点分割で切られないか（§6.2） |

後ろ2つは rev.3 で追加。**Ex Tap を独立した kind として実装せず、この2属性で表現する**ため。
こうすると将来「Ex Slide 始点」「Ex Flick」が欲しくなっても表に1行足すだけで済む。

### 1.4 種別プリセット

| kind | points | startTrigger | sustain | motion | resolution | judgeProfile | chainExempt |
|---|---|---|---|---|---|---|---|
| **Tap**    | 1  | `Contact` | None | None | **Cell** | Normal | false |
| **Ex Tap** | 1  | `Contact` | None | None | **Cell** | **AllPerfect** | **true** |
| **Slide**  | ≥2 | `Contact` | **Ticks** | None | **Continuous** | Normal | false |
| **Flick**  | 1  | `Presence` | None | **Flick** | **Continuous** | Normal | false※ |

※ Flick は `chainExempt = false` だが、**早い側だけ中点分割を適用しない**という
片側だけの例外を持つ（§6.2）。属性としての真偽値では表せないので、
`chainExempt` を将来 `None / Early / Both` の3値に昇格させる余地を残す。

**新種別を足す手順**: `NoteKind` に値を足し、この表に1行足し、必要なら
見た目用のパラメータ構造体を足す。判定側は属性を見て動くので `switch` は増えない。

### 1.5 Ex Tap

**通常 Tap の派生**。判定窓内なら必ず PERFECT+、外れれば MISS。

- 判定窓は **±100.00ms**（通常 Tap の GOOD 窓と同じ幅）。この中は**すべて PERFECT+**。
- **縦連判定の影響を受けない**（`chainExempt = true`）。自身の窓は中点で切られない。
- ただし**他ノーツから見た中点境界としては機能する**。つまり Ex Tap の隣にある
  通常 Tap は、Ex Tap との中点で窓を削られる。Ex Tap 側だけが得をする非対称な関係。
- 通常 Tap とは**色などの見た目で区別**する。
- 用途: Slide 追従中の指による誤爆が起きうる位置に置いて、巻き込まれても最高判定にする（§6.3）。
- スコア上は PERFECT+ なので `1.01` 倍で加算される（§7）。

## 2. Slide（旧 Hold + 旧 Arc の統合）

旧 Hold と旧 Arc はデータ構造が完全共通で、違いは判定解像度だけだった。
**統合して Slide 1種にする**ことで、区別のための概念が丸ごと消え、
種別が Tap / Slide / Flick の3系統になる（理解負荷の低減が主目的）。

- **操作は「なぞる」**。「押さえ続ける」はこれに包含される
  （全 Waypoint が同じ位置の Slide ＝ 旧 Hold）。
- **層は連続値**（`layerF ∈ [0,1]`）を取り、層をまたぐ軌跡を書ける。
- **幅は 1〜12 セルの任意の値**（データは float、エディタでスナップ）。
- **判定解像度は連続座標**（§0.2）。

### 2.1 判定モデル: 「等間隔に並んだ判定点の列 + 見た目の帯」

Slide は全体を1つの状態機械で扱わない。**コンボ点（判定点）を独立に判定する**。

- 各コンボ点の時刻に、いずれかの接触点が Slide の帯の内側にあれば成立。
- **一度逃して MISS になっても、途中から押し直せば残りのコンボ点は成立する。**
- これにより旧実装の「HOLD BREAK（0.2 秒離れたら丸ごと失敗）」という状態機械が消える。
- **始点のコンボ点のみ枠内更新（`Contact`）を要求**し、以降のコンボ点は
  「その時刻の前後に枠内へ入力が存在したか」だけを見る（§2.4）。
  始点は枠内更新で駆動されるため、**同時刻の Tap / Ex Tap と同じ入力イベントで
  まとめて解決される**（§0.2 / §6.4）。包含判定は始点も連続座標のままなので、
  中間層（`layerF ≈ 0.5`）から始まる Slide も書ける。

**帰結**: 総ノーツ数（＝理論値）が Slide の長さに依存する（意図どおり）。
難度表記・スコア計算式はこれを前提にする。

### 2.2 コンボ点の生成規則

コンボ点は **Slide 全体を通した連続した刻み**で生成する。**区間ごとに刻み直さない。**

```
コンボ点集合 =
    { Slide 始点 points[0] }        // marker 不問・無条件
  ∪ { Slide 終点 points[^1] }       // marker 不問・無条件
  ∪ { Visible 中継点 }              // §3
  ∪ { 始点から comboStep 刻みで進んだ点（始点自身は除く／終点を超えない範囲） }
（時刻が完全に一致するものは1つに統合）
```

- **始点と終点は `marker` に関わらず無条件でコンボ点。**
  始点・終点にとっての `marker` は「Tap 型のマーカーを重ねて描くか」という
  **見た目の指定にすぎず**、コンボ点になるかどうかには影響しない。
  （帯そのものは `marker` に関わらず始点から終点まで描かれる。）
- **Invisible 中継点と `None` の制御点はコンボ点にならない**（形状の制御にのみ使う）。
  自動生成が「区間の始点」を特別扱いしないのもこのため。

**中継点は刻みの位相をリセットしない。**
自動生成は Slide 始点だけを基準に、Slide 全体を `comboStep` 刻みで打つ。
これにより、**形状のために中継点をいくつ増やしてもコンボのリズムが乱れない**。

- 唯一の例外が `comboStep` の変わる点で、そこは §2.3 により **Visible 中継点が必須**。
  必ずコンボ点が打たれるので、新しい刻み幅はその点を基準に自然に再開する。
  **この必須ルールは、区間にとらわれない連続刻みを成立させるための条件**であり、
  §2.3 の要求と本節の規則は一体で読む必要がある。
- **端数**（最後の自動生成点から終点までの `comboStep` 未満の区間）**にはコンボ点を打たない。**
  終点が無条件コンボ点なので、そこで終わる。端数を次に持ち越すこともしない。

**コンボ点の近接は許容する。**
Visible 中継点を自動生成点のすぐ隣に置けば、間隔は `comboStep` より短くなりうる。
§2.3 の「毎秒 4〜8 コンボ」は**最低密度の保証であって上限ではない**ので、これは意図した挙動。
**近接を理由とした間引きは行わない**（統合するのは時刻が完全に一致する場合のみ）。

### 2.3 コンボ刻み幅（`comboStep`）の決定

**規則: 刻みの実時間が 0.125〜0.25 秒（毎秒 4〜8 コンボ）に収まる音価を選ぶ。**

これは **Slide コンボ点の「最低密度」を保証するための規則**であって、密度の上限ではない。
Visible 中継点によってこれより密になるのは許容する（§2.2）。

| BPM 帯 | 音価 | 刻みの実時間 | tick 数（`ticksPerBeat=5040`） |
|---|---|---|---|
| 30〜59 | 32分 | 0.250 → 0.127s | 630 |
| **60〜119** | **16分** | 0.250 → 0.126s | **1260** |
| **120〜239** | **8分** | 0.250 → 0.126s | **2520** |
| **240〜479** | **4分** | 0.250 → 0.126s | **5040** |
| 480〜959 | 2分 | 0.250 → 0.125s | 10080 |

太字がユーザー指定分。境界の 60 / 120 / 240 は上記の帯の切れ目そのものなので、
規則を実時間で持てば表外の BPM も自動で決まる。

- **BPM が変化する場合、その境界時刻に `marker = Visible`（ノーツ型）の中継点を置くことを
  必須とする。** §2.2 のとおり刻みの位相は中継点でリセットされないため、
  `comboStep` が変わる点にコンボ点が無いと刻みが破綻する。
  Visible 中継点なら必ずコンボ点になるので、そこを基準に新しい刻みが再開できる。
  置かれていない、または Invisible の場合は**エディタ側で警告を出す**。
- `Waypoint.comboStep` による**上書きを許可**する（null なら上記表から自動決定）。
  BPM 119 と 120 で刻みが倍違うため、境界付近の曲で作者の意図と異なる方を
  引く可能性があるのを救う。
  **上書きを行う Waypoint も `marker = Visible` でなければならない**（理由は上と同じ。
  刻み幅が変わる点には必ずコンボ点が要る）。こちらもエディタ側で警告を出す。

### 2.4 コンボ点の判定（始点以外）— 時間対称

**始点以外のコンボ点（自動生成点・Visible 中継点・終点）は、押す必要も離す必要もない。**
その時刻に帯の内側を占有していれば最高判定。離れていた場合は
**最後に／最初に帯の内側にいた時刻から逆算**して判定を出す。

```
コンボ点 p（時刻 t_p）について:
  S = { s ∈ [t_p - 100ms, t_p + 100ms] : 時刻 s に帯の内側へ接触点があった }

  S が空           → MISS
  そうでなければ    dt = min_{s ∈ S} |s - t_p|  → §6.1 のティア表でティアを決定
```

- **押し続けていれば `t_p ∈ S` なので `dt = 0` → PERFECT+。**
  これが「なぞり続けていれば理論値が取れる」ことを保証する。
- **時間的に対称**。早く離した場合も、遅れて掴んだ場合も同じ式で扱う
  （`t_p` の 60ms 前に離した ＝ `t_p` の 60ms 後に掴んだ、どちらも PERFECT）。
- 対称にしたため**各コンボ点の確定は `t_p + 100ms`**（指が戻ってくる可能性があるため
  それまで待つ）。判定表示の遅れはノーツ演出側で吸収する（演出仕様は別途）。
- **終点も同じ規則**。終点で指を離す動作は要求しない。
- **始点だけは例外**で、通常の Tap と同じく枠内更新（`Contact`）を要求し、
  §6.1 のティア表と §6.2 の縦連判定をそのまま適用する。

## 4. Flick

**判定方式は「座標移動」**（接触点の NDC 座標の移動量を見る）。
セル更新の複数回検出は**不採用**——セル境界のすぐ横で始めたフリックは 1px で成立し、
セル中央で始めたフリックはセル幅の半分動かないと成立しない、という
**成否の位置依存**が音ゲーとして致命的なため。

### 4.1 成立条件

**「枠内に接触点が存在」かつ「直近 `flickWindowMs` の移動量が `flickDistance` 以上」**。

- **新規接触は不要**。既に動いている指が枠内を擦り抜けても成立する
  （`startTrigger = Presence`）。**本質は枠内の移動**であって、接触の開始ではない。
- 成立タイミングは**移動量が閾値を超えた瞬間**の時刻。この時刻で判定窓を評価する。
- 実装には `Contact` に「直近 `flickWindowMs` 分の `(u, v, time)` リングバッファ」が要る。
- **1回のフリック成立で消費するノーツは1個**（条件を満たす未処理ノーツのうち**最も早いもの**）。
  成立後はその接触のリングバッファをリセットする（同じ移動履歴で次が即成立するのを防ぐ）。

### 4.2 移動量の閾値

**`flickDistance` = 最小パネル横幅 0.5 セル分。**

現行値（`U = 0.87`, `cells = 12`）だと 1セル幅 = `2 × 0.87 / 12 = 0.145` NDC なので、
**閾値は 0.0725 NDC**。仮値 0.06（≒0.41 セル）よりわずかに厳しくなる。

- **方向は不問**（`flickDirection = Any`）。縦方向のフリックも成立する。
- **移動量は `√(Δu² + Δv²)`（ユークリッド距離）で測る。閾値だけ横幅基準（0.0725）とし、
  方向は不問。** 縦フリックも横フリックも同じ閾値で成立する。

### 4.3 判定窓（早い側に非対称）

**基本は Tap と同じ4段**（§6.1）。**その上で、早い分はすべて PERFECT+ に繰り上げる。**

| 判定 | dt = 入力時刻 − ノーツ時刻 |
|---|---|
| **PERFECT+** | `-100.00 ≤ dt ≤ +33.33` |
| **PERFECT**  | `+33.33 < dt ≤ +66.67` |
| **GOOD**     | `+66.67 < dt ≤ +100.00` |
| **MISS**     | それ以外（窓外の入力は拾わない） |

- 早い側の上限は **-100ms**（Tap の窓と同じ）。無制限ではない。
- **フリック自身は早い側の縦連判定（中点分割の下限）を受けない**（§6.2）。

### 4.4 移動が確認できなかった場合

判定窓を過ぎた時点（`t_N + 100ms`）で、窓内の入力状況によって結果を分ける。
**Tap の離散イベント基準に合わせる**:

| 窓内の状況 | 結果 |
|---|---|
| 移動量が閾値を超えた | §4.3 の窓で PERFECT+ / PERFECT / GOOD |
| 移動なし、**枠内更新が1度以上あった** | **GOOD** |
| 移動なし、**接触は存在するが枠内更新なし** | **MISS** |
| 窓内に接触が存在しない | **MISS** |

### 4.5 パラメータ

| 名前 | 意味 | 値 |
|---|---|---|
| `flickDistance` | 成立に必要な NDC 上の移動量 | **0.5 セル幅（現行値で 0.0725）** |
| `flickWindowMs` | その移動を行うべき時間窓 | **未定**（仮 120 ms、実機で決定） |
| `flickDirection` | `Any` / `Left` / `Right` / `Up` / `Down` | **`Any` のみ実装**（他はフィールドのみ予約） |

## 5. 時間軸（tick）とスクロール

### 5.1 確定事項

- 譜面上の時刻は **拍ベースの tick**。**`ticksPerBeat = 5040`**（int）。
- tick は**譜面先頭からの累積値**（前のノーツからの差分ではない）。
  差分方式は途中挿入で以降が全部ずれるため採らない。
- 秒への変換: `秒 = tick / ticksPerBeat × (60 / BPM)`。
  BPM 変化には `bpmEvents: (tick, bpm)[]` を持ち、
  **譜面ロード時に1回だけ** tick→秒 の変換テーブルを構築する。
- ランタイム（`NoteRuntime` / `NoteGeometry` / 頂点に焼く値）は**秒のまま**。
  変換を譜面フォーマット層に閉じ込め、既存の描画・判定への影響を最小化する。

### 5.2 `ticksPerBeat = 5040` を選んだ理由

- `5040 = 2^4 × 3^2 × 5 × 7`。**1〜10 のすべてで割り切れる**（LCM(1..10)=2520 の性質を維持）。
- **`5040 / 16 = 315` → 64分音符まで整数**。
  2520 だと `2520/16 = 157.5` で 64分音符が表現できない（2 の因数が3つしかない）。
- 3連系も整数: `/12 = 420`、`/24 = 210`、`/48 = 105`。
- 1920 / 960 は 7 で割り切れないため、7連符を使う余地がなくなる。
- コストは無視できる。5分・BPM200 の曲で 1000拍 × 5040 = 504万 tick、
  int32（上限 21億）に十分収まる。変換はロード時1回きり。

### 5.3 なぜ実時間ベース（2520 tick/秒）を採らないか

**音価が整数 tick にならない**ため。譜面フォーマットとして致命的。

```
BPM 130 の8分音符 = 0.230769s × 2520 = 581.538 tick   ← 非整数
BPM 133 の4分音符 = 0.451128s × 2520 = 1136.842 tick  ← 非整数
```

大半の BPM で 4分音符すら整数にならず、丸めれば 16分連打で誤差が累積して曲とずれる。
拍ベースなら音価は BPM に関係なく常に整数（4分 = 5040、8分 = 2520、16分 = 1260、
3連 = 1680、7連 = 720）。加えて:

- エディタで拍にスナップできる（譜面は「16分の3つ目」で置くもので、秒では置かない）
- BPM を後から直したとき譜面全体が自動追従する（実時間ベースだと全打ち直し）
- §2.3 の「BPM で刻み幅を決める」仕様が自然に書ける（8分 = `ticksPerBeat/2`）

### 5.4 「時刻」「表示位置」「スクロール速度」の3層分離

| # | 概念 | 何で決まるか | 判定への影響 |
|---|---|---|---|
| 1 | **時刻**（いつ叩くか） | tick + BPM → 秒 | **あり** |
| 2 | **表示位置**（画面のどこに描くか） | 時刻 + スクロール速度 | **なし** |
| 3 | **スクロール速度** | ソフラン等のギミック | **なし** |

現行コードも既にこの分離になっている（位置はデータとして持たず、毎フレーム導出）:

```
depth = zJudge + (noteTime - songTime) * speed
```

### 5.5 ソフラン（確定）

**ソフラン = 譜面が流れる速度が変化すること。** 速度は時間ではなく**倍率**で持つ。

#### 速度の表現

`readAheadSec`（現行 1.2）は「**倍率 1.0 のときの基準先読み時間**」として内部に残し、
プレイヤーが触るのは `hiSpeed` 倍率だけにする。

```
実効速度  speed(t) = baseSpeed × hiSpeed × scrollMul(group, t)
baseSpeed = (zFar - zJudge) / readAheadSec        // 現行の StageDerive のまま
```

表示位置は倍率の積分で決まる:

```
X(t)  = ∫₀ᵗ scrollMul(group, τ) dτ
depth = zJudge + (X(noteTime) - X(songTime)) × baseSpeed × hiSpeed
```

実装上は**頂点に焼く値を「時刻」から「表示位置 X(noteTime)」に変え、
uniform を `X(songTime)` にする**だけで済み、**判定には一切触れない**。

#### イベント形式

```
scrollEvents : (tick, group, mul, easing, durationTicks)[]
```

- **既定は階段状**（`durationTicks = 0` で直ちに変化）。
- **補間ありに切替可能**。`durationTicks > 0` のとき、前の倍率から `mul` まで
  `easing`（§1.2 の列挙を再利用）に従って `durationTicks` かけて遷移する。
- **`mul = 0`（停止）と `mul < 0`（逆走）を許す。** どちらも `X(t)` の積分がそのまま扱う。
  - 停止: `X(t)` が平坦になるだけ。実装コストなし。
  - 逆走: ノーツが判定線を通り過ぎてから戻る。現行 `Note.shader` は
    `depth > _Far` でしか discard していない（手前側は判定済みフラグ `state` で消える）ため、
    **未判定ノーツは判定線より手前でも描かれ続ける＝逆走はそのまま動く**。
    ただし**一度判定が確定したノーツは逆走で戻ってきても再表示されない**。

#### スクロールグループ

ノーツ個別のスピード指定は持たず、**スクロールグループ**（`Note.scrollGroup`、既定 0）を導入する。
グループごとに独立したソフランをかけ、それを重ねることで実質的に個別指定を実現する。

- グループは**地上/空中の層とは独立**。同じグループに地上ノーツと空中ノーツを混在できる。
- 同一グループ内の全ノーツは同じ `X(t)` を共有する。
- 実装上は uniform `X(songTime)` をグループ数ぶん持ち、描画をグループ単位でバッチする。
- **グループ数に上限を設けない。**
- **描画順は手前から**（グループ番号や生成順ではなく、奥行き `depth` の手前優先で描く）。
- **可視性・不透明度など、スクロール以外の属性はグループに持たせない。**
  グループは純粋にスクロール速度だけを束ねる概念。

## 6. 判定ティアと縦連判定

### 6.1 判定ティア（確定）

**ティアは配列データとして持つ**（列挙型 + `switch` にしない）:

```
JudgeTier[] = [ (name, halfWidthMs, scoreWeight, comboBreak) ]
```

| ティア | 判定窓 (halfWidth) | スコア係数 | コンボ |
|---|---|---|---|
| **PERFECT+** | **±33.33 ms** | **1.01** | 継続 |
| **PERFECT**  | **±66.67 ms** | **1.00** | 継続 |
| **GOOD**     | **±100.00 ms** | **0.50** | 継続 |
| **MISS**     | （上記の外） | **0.00** | **切断** |

- 33.33 / 66.67 / 100.00 ms は 60fps の **2 / 4 / 6 フレーム**に対応する。
- **±100ms の外の入力は一切拾わない。** 空打ちにペナルティはなく、入力も消費されない
  （MISS の暴発を防ぐため）。**MISS はノーツ側のタイムアウトでのみ発生する。**
- `judgeProfile = AllPerfect`（Ex Tap）は、この表を無視して**窓 ±100ms 内を常に PERFECT+**、
  外は MISS とする。
- Flick は早い側だけ非対称（§4.3）。
- Slide の始点以外のコンボ点は §2.4 の `dt` でこの表を引く。

### 6.2 縦連判定（中点分割）

**目的**: ノーツ間隔が極端に短いとき、入力の暴発が次のノーツを不利な判定で
食ってしまうのを防ぐ。代償として判定窓が狭くなり MISS は出やすくなる。

**適用範囲は文字どおり「縦に連なった配置」のみ。**
下記の「同一 layer かつセル範囲が交差する」という条件がそれを表しており、
**トリル（交互打ち）や階段配置は別セルなので対象外**。これは意図した仕様。

**規則**:

```
対象集合 T = { Tap, Ex Tap, Flick, Slide の始点 }

ノーツ N ∈ T について、同一 layer かつセル範囲が交差する N' ∈ T のうち、
  prev(N) = t_{N'} < t_N を満たす最近傍
  next(N) = t_{N'} > t_N を満たす最近傍

  loBound(N) = prev があれば (t_prev + t_N) / 2、なければ -∞
  hiBound(N) = next があれば (t_N + t_next) / 2、なければ +∞

  実効窓(N) = [t_N - W_worst, t_N + W_worst] ∩ [loBound(N), hiBound(N)]
```

`W_worst` = 最下位ティア（GOOD）の半幅 = **100 ms**。

**適用の例外**:

- **`chainExempt = true`（Ex Tap）は自身の窓を切られない**（実効窓 = 素の窓 ±100ms）。
  ただし**他ノーツの `prev` / `next` としては機能する**。つまり Ex Tap の隣の通常 Tap は
  Ex Tap との中点で削られる。Ex Tap 側だけが得をする非対称な関係で、これは意図的。
- **Flick は早い側だけ免除**: `loBound` を適用せず、`hiBound` のみ適用する。
  早い分がすべて PERFECT+（§4.3）である仕様と揃える。

**その他**:

- **ティアごとの処理は不要。全ティア共通の1本の窓を中点で切るだけ。**
  判定ティアは切った後の窓の中で通常どおり `|dt|` で決まる。
- **Slide の途中コンボ点は対象外**（対象は始点のみ）。
- **層が違えば無関係**（別の手で押す想定）。
- MISS は `songTime` が実効窓の上限を超えた時点で確定する
  （素の窓より早く確定するため、次のノーツを叩く前にフィードバックが返る）。

**効き方（縦連時の実効窓）**: 一様な間隔 Δ の縦連では実効窓が `[-Δ/2, +Δ/2]` になるので、

| 実効窓 | 消えるティア | 該当密度 |
|---|---|---|
| `Δ ≤ 133.3 ms` | **GOOD が構造的に消える** | 16分で BPM 112.5 以上 / 8分で BPM 225 以上 |
| `Δ ≤ 66.7 ms` | PERFECT も消え **PERFECT+ か MISS のみ** | 16分で BPM 225 以上 |

**実用域の16分縦連ではほぼ GOOD が出ない**が、これは意図した仕様
（縦連は「縦に連なった配置」に限定されるため、トリルや階段には影響しない）。

**現行実装との差分**: 現行 `Judge.OnEnter` は既に「候補の中から `|dt|` 最小のノーツを
選ぶ」実装で、中点分割は「入力を時間的に最も近いノーツに帰属させる」ことと数学的に
等価なので、**帰属の部分は実質すでに入っている**。実際に変わるのは次の2点で、
ここが縦連判定の本体:

1. **解決済みノーツの領域に落ちた暴発入力が、次のノーツを食わなくなる。**
   現行は候補を Pending に限るため、A を叩いた直後の暴発が、窓が後ろに伸びている
   B（素の窓 [-20, +180]）に届いて GOOD で食ってしまう。中点で切れば B は到達不能になり、
   暴発はどのノーツにも当たらず無害に落ちる。
2. **MISS の確定タイミングが早まる**（上記）。

**実装**:

- 中点は距離に対して単調なので、**「全ペアを見る」と「前後それぞれの最近傍だけを見る」は
  結果が同一**（B から見て、より遠い D の中点は必ず C の中点より外側にある）。
  よって **前後の最近傍のみ**で実装する。
- 譜面ロード時に **O(n) で precompute**。実行時コストはゼロ。
- 走査の打ち切り条件が「全ノーツ共通の窓」から「ノーツ固有の実効窓」に変わるため、
  現行 `Judge` の `cursor` 走査ロジックに修正が要る。
- **同一層でセル範囲が交差する同時刻ノーツは許可する**（§6.4）。
  `prev` / `next` の定義が**厳密不等号**（`t_{N'} < t_N` / `t_{N'} > t_N`）なので、
  同時刻ノーツは互いの `prev` にも `next` にもならず、**式を一切変えずに
  同時刻グループ内の縦連判定が無効になる**。グループの外にある前後の最近傍とは、
  通常どおり中点で窓が切られる。
  > rev.3 までは「中点が自分自身の時刻になって窓が潰れるのでエディタ側で禁止する」と
  > 記述していたが、これは誤り。厳密不等号のため窓は潰れない。rev.4 で撤回。

### 6.3 Slide 追従中の指による Tap 誤爆について

**接触点の除外はしない**（rev.1 の「拘束済み接触点の除外」ルールは**不採用**）。

Slide をなぞっている指がセル/バンド境界をまたぐと枠内更新が発生し、通りがかりの
Tap を誤爆しうるが、これは**想定内**とする。対策は次の2本立て:

1. **Ex Tap（§1.5）を置く。** 誤爆が起きうる位置には Ex Tap を配置し、
   巻き込まれても最高判定になるようにする。Ex Tap は縦連判定も受けないため、
   どれだけ巻き込んでも PERFECT+ が保証される。
2. **譜面編集のレギュレーションで縛る。** 通常 Tap と Ex Tap は併用するので、
   Ex Tap で救えない箇所は配置側で避ける。§0.1 のバンド分割で更新イベントが増えるぶん、
   レギュレーション側の負荷は上がる。

### 6.4 同時刻ノーツ（セル範囲の交差を許可）

**同一層でセル範囲が交差する同時刻ノーツを許可する。**
1本の指で複数ノーツを同時に取らせる配置を、意図的な表現手段として使えるようにする。

**規則**:

1. **縦連判定は同時刻グループ内でのみ無効。**
   §6.2 のとおり `prev` / `next` が厳密不等号なので、追加の実装は不要。
   グループの外にある前後の最近傍とは、通常どおり中点で窓が切られる。
   （グループ全体を縦連判定から外すことは**しない**。それを許すと同時刻ノーツを2枚
   重ねるだけで縦連判定を回避でき、そのために用意した Ex Tap の意味が薄れるため。）

2. **1回の枠内更新で、該当するノーツをすべて同時に解決する。**
   対象は「**同じ枠内更新で駆動される**（§0.2）＋ **同時刻** ＋ **入力位置が包含判定を満たす**」
   ノーツの全体。すなわち **Tap / Ex Tap / Slide 始点**。
   **Flick は駆動が「移動量の閾値超過」で異なるため、同時刻でも独立に判定する。**

3. **`dt` は共通だが、ティアは同じとは限らない。**
   まとめて解決されるのは「同じ入力イベントで、同じ `dt` を使って」という意味であって、
   結果のティアが揃うわけではない。同時刻に通常 Tap と Ex Tap を交差配置した場合、
   同じ `dt` でも Ex Tap は PERFECT+（`judgeProfile = AllPerfect`）、
   通常 Tap は `dt` 相応のティアになる。

4. **コンボ・スコアはノーツの数だけ加算する。**
   1回の入力で2ノーツ解決すればコンボは2進み、スコアも2ノーツ分入る。
   §7 の総ノーツ数 `N` も当然2として数える。

**実装上の注意**: 「交差範囲」を明示的に計算する必要はない。
**「入力位置を自分の包含範囲に含む同時刻ノーツをすべて解決する」**で同じ結果になる
（交差部分を押せば両方が該当し、片方だけの範囲を押せば片方だけが該当する）。
現行 `Judge.OnEnter` は「候補から `|dt|` 最小のノーツを1つ選ぶ」実装なので、
**選んだノーツと同時刻の該当ノーツもまとめて解決する**よう変更が要る。

**エディタ要件**: セル範囲の交差は**意図的な配置**なので、警告ではなく
**交差している範囲をハイライト表示する**情報提示とする（作者が交差の有無を目視できればよい）。

## 7. スコア（確定）

**1ノーツあたりの素点（NotePoint, NP）は譜面の総ノーツ数で決まる。**

```
NP = 1,000,000 / N        // N = 総ノーツ数
スコア = NP × (1.01 × [PERFECT+ 数] + 1.00 × [PERFECT 数] + 0.50 × [GOOD 数])
```

- **`N` は総コンボ点数**。Tap / Ex Tap / Flick はそれぞれ 1、
  Slide は **その Slide が持つ全コンボ点の数**（§2.2）を数える。
  総ノーツ数が Slide の長さに依存するのは**意図どおり**。
- **丸めはノーツごとに行わず、最後に一度だけ行う。** 整数演算で:

  ```
  score = round( 1,000,000 × (101 × P⁺ + 100 × P + 50 × G) / (100 × N) )
  ```

- これにより理論値がちょうど整数になる:
  - 全 PERFECT+ → **1,010,000**（上限）
  - 全 PERFECT  → **1,000,000**
- MISS は係数 0 かつコンボ切断。
- Ex Tap は窓内なら必ず 1.01 倍で加算される。
