## 1. 「空中のほうが速い」— 調査結果

### 1.1 結論

**プログラム側にバグは無い。設計どおりの挙動で、原因は幾何（透視圧縮）にある。**
ユーザーの体感は正しく、定量的にも裏付けられる。

### 1.2 計測

`memory/settings.json`（実機チューニング済みの値）で、`StageDerive` と同じ式を
Node 側に再実装して実測（スクリプトは `memory/verify/` の既存手法と同じ使い捨て運用）。

導出値: `zJudge = 3.100`, `skyHeight = 6.123`, `zFar = 78.450`, `speed = 62.79`,
`vHorizon = 0.982`, `vFar = 0.791`, `vFarSky = 0.935`。

| | 判定線での画面速度 (NDC v/秒) | レーンの画面上の長さ (NDC v) | 判定線でのノーツ幅比 | **自レーン長で正規化した速度** |
|---|---|---|---|---|
| Ground | 11.63 | 1.541 | 1.000 | 7.54 /秒 |
| Sky | 11.43 | **0.785** | **0.488** | **14.56 /秒** |
| 比 (Sky/Ground) | 0.983 | 0.509 | 0.488 | **1.931** |

**絶対的な画面速度（ピクセル毎秒）はほぼ同じ**（0.983倍、これは現行パラメータでの偶然に近い一致）。
差が出るのは「何に対して速いか」で、**空中レーンは画面上の長さもノーツの幅も地上の約半分**。
同じピクセル速度でも自分のレーン長・自分の大きさに対しては約1.93倍動くので速く見える。

時刻ごとの推移（判定線到達までの残り時間 t）:

| t (秒前) | 奥行き | v (Ground) | v (Sky) | 自レーンの残り割合 (G) | 同 (S) |
|---|---|---|---|---|---|
| 0.0 | 3.10 | -0.750 | 0.150 | 0% | 0% |
| 0.1 | 9.38 | -0.054 | 0.632 | 45% | 61% |
| 0.2 | 15.66 | 0.243 | 0.760 | 64% | 78% |
| 0.4 | 28.22 | 0.512 | 0.854 | 82% | 90% |
| 0.8 | 53.33 | 0.710 | 0.913 | 95% | 97% |
| 1.2 | 78.45 | 0.791 | 0.935 | 100% | 100% |

**判定線の 0.2 秒前の時点で、地上ノーツは自レーンの 36% を消化済みなのに空中ノーツは 22% しか
消化していない。**残りを同じ 0.2 秒で走り切るので、空中側は終盤の詰め込みがきつく「最後に
一気に来る」＝速いという体感になる。

### 1.3 なぜそうなるのか

判定線の奥行き `zJudge` と最遠端 `zFar` を両層で共有する設計
（`muses-stage-ui-design` 2026-07-29 改訂）の必然的な帰結。

- 層で共通の奥行きを使う → **速度もワールド空間では完全に同一**（`Derived.speed` は1つしかない）。
  これはタイミングを層非依存にするための意図的な設計であり、ここは変えるべきではない。
- 一方、画面への写り方は面の高さで決まる。カメラ `yCam = 8.0` に対し
  **空中面は `skyHeight = 6.123`＝カメラとの高低差がわずか 1.877**（地上は 8.0）。
  高低差が小さいほど `v = tan(θ − atan(h/z)) / tan(φ/2)` の z 依存が急峻に飽和し、
  同じ奥行き範囲が画面上の狭い帯に圧縮される。
- 同じ理由でノーツの横幅も圧縮される（空中面は判定線でカメラに近く、
  ワールド幅が地上の 0.488 倍で同じ画面幅に収まる）。

この「空中の助走距離が短い」問題は `muses-stage-ui-design` で一度検出され、
2026-07-29 の zFar 共有化で 0.57 → 0.71 NDC まで改善済み。現行値では 0.785 まで来ているが、
**地上の半分という構造は残っている**。

### 1.4 効くパラメータ・効かないパラメータ

`ratio` = 自レーン長で正規化した速度比（Sky/Ground）。1.0 に近いほど両層の体感速度が揃う。

| パラメータ | 動かす向き | ratio への効き |
|---|---|---|
| **`phiDeg`（垂直画角）** | **下げる** | **最も効く**。77 → 70 で 1.70、→ 65 で 1.57、→ 60 で **1.46** |
| `thetaDeg`（俯角） | 下げる | 38 → 34 で 1.72、→ 30 で 1.56。ただし地上の span も縮む |
| `vSkyJudge` | 下げる | 0.15 → 0.05 で 1.83。効きは小さく、`vSplit = -0.1` に近づけると層分離が苦しい |
| `vGroundJudge` | 上げる（-0.75→-0.45） | 1.46 まで下がるが地上 span が 1.54 → 1.27 に縮む |
| `farFrac` | 下げる | 0.9 → 0.6 で 1.62。ただし先読み距離そのものが縮む |
| **`yCam`** | — | **完全に無効**。全長がスケールするだけで ratio は 1.931 のまま変化しない |

**`yCam` をいじっても何も変わらない**のは重要な知見（幾何が相似変換になるため）。
実機調整で最初に触りたくなるパラメータだが、時間の無駄になる。

組み合わせの実測（`farFrac = 0.9` 固定）:

| phiDeg | thetaDeg | vSkyJudge | spanG | spanS | **ratio** | 幅比 | vHorizon |
|---|---|---|---|---|---|---|---|
| 77 | 38 | 0.15 | 1.541 | 0.785 | **1.931** (現行) | 0.488 | 0.982 |
| 70 | 38 | 0.15 | 1.575 | 0.877 | 1.704 | 0.545 | 1.116 |
| 65 | 38 | 0.15 | 1.575 | 0.937 | 1.569 | 0.583 | 1.226 |
| **60** | **38** | **0.15** | **1.575** | **0.996** | **1.459** | 0.620 | 1.353 |
| 60 | 34 | 0.15 | 1.575 | 0.889 | 1.406 | 0.669 | 1.168 |
| 60 | 30 | 0.15 | 1.557 | 0.781 | 1.356 | 0.714 | 1.000 |

**推奨**: まず `phiDeg` を 77 → 60〜65 に下げるところから試す。
空中 span が 0.785 → 0.94〜1.00（+20〜27%）に伸び、幅比も 0.49 → 0.58〜0.62 に改善する。
地上 span はむしろ微増（1.541 → 1.575）するので地上側の犠牲がない、という点で単独の最有力候補。
代償は画角が狭まって遠近の誇張が弱まること（見た目の好みの問題）と、
`vHorizon > 1`＝地平線が画面外に出ること（`showHorizon = false` なので実害なし）。

**ratio を 1.0 にはできない。**それには空中面をカメラから地上面と同じだけ離す必要があり、
空中面が地上面と同じ高さになる＝層が消える。**1.3〜1.5 程度が構造上の実用下限**と考えてよい。

### 1.5 「ステージが平行に見えない」について

これは**仕様どおり**で、2つの別の事実が混ざっている可能性がある。

1. **両層のパネルはワールド空間では厳密に平行**（どちらも水平面、y=0 と y=skyHeight）。
   画面上で平行に見えないのは高低差による透視の違いによるもので、避けようがない。
2. **最遠端の「断面」は長方形になるよう補正済み**（`Derived.zcFarGround` による層別 `c` 補正、
   `muses-stage-ui-design` 2026-07-29 追記）。実測でも両層の最遠端 screenU は一致する。
3. **手前側の端は揃っていない**。`skyFloorFromJudge = true` のため空中パネルは判定線
   （v=0.15）で切られるのに対し、地上パネルは `vGroundBot = -1.0` まで伸びる。
   さらに空中パネルは画面上 v ∈ [0.15, 0.935] を占め、**地上パネルの遠方部分
   （v ∈ [0.15, 0.791]）と画面上で重なる**。この重なりが「平行でない」印象の主因かもしれない。

→ **どの部分を指しているかスクリーンショットで確認したい**。3 が該当するなら
`skyFloorFromJudge` を false にする（空中パネルを `vSkyBot = -0.1` まで下ろす）か、
`farFrac` を下げて重なりを減らす方向が対処になる。1・2 が該当するなら仕様どおりで打つ手はない。

### 1.6 このテーマの結論

**コード変更は不要**。ユーザー側でのパラメータ調整で対応する方針でよい。
上記の表を調整の出発点として使えばよく、**`yCam` は触らないこと**、
**`phiDeg` から試すこと**の2点だけ覚えておけばよい。

### 1.7 【2026-08-06 改訂】§1.1〜§1.6 の結論は誤り。コード修正で ratio = 1.000 を達成した

**`phiDeg` によるパラメータ調整は不要になった。§1.4 の表と §1.6 は破棄してよい。**

きっかけはユーザーからの別の指摘: **Riser の壁（同時刻の地上端と空中端を結ぶ垂直な壁）が
画面上で台形に傾く**。実測すると壁の上端と下端の画面 x は最大 **27.8%** ずれていた
（判定線と最遠端では 0%、中間で最大）。調べると **これは §1 の「空中が速く見える」と同一の原因**だった。

**見落としていた事実**: 各層のパネルは `zcFarGround` による層別収束補正のおかげで、
**画面 x に関して互いに厳密な射影像**になっている。§1.5-2 は「最遠端の断面は長方形になるよう
補正済み」と最遠端についてのみ述べていたが、実際は**帯の全域**でこの性質が成り立つ。
つまり「地上レーンの画面上の進み具合 p」で層をパラメータ化すれば、
**同じ p の地上と空中は画面 x が厳密に一致する**（全層・全奥行きで数値誤差レベル、Python 検証済み）。

ズレていたのは**ステージ構造ではなくノーツの置き方**だった。共有ワールド奥行き `d0` は
「タイミングの正」ではあっても「画面上の進み具合の正」ではない。§1.3 は「層で共通の奥行きを使う」
ことを ratio 1.93 の必然的帰結として扱ったが、**共通なのはタイミングだけでよく、描画位置まで
共通にする必要はなかった**。§1.6 の「ratio 1.0 は原理的に不可能（空中面が地上面と同じ高さに
なってしまう）」は、面の高さを変える方向しか検討していなかったことによる誤りである。

**修正**（`Assets/Shaders/Include/NotePlacement.hlsl` の `PlaceNote`、頂点シェーダのみ）:
地上ノーツが自レーンの p% を消化した瞬間、層 L のノーツも自レーンの p% の位置に置くよう
**層ごとに奥行きを再マップ**する。判定線 (p=0) と最遠端 (p=1) はどちらも従来と同じ奥行き
(`_ZJudge` / `_Far`) に落ちるので、**パネルの描画範囲・near/far フェード・判定・
`Derived` の導出値は一切変わらない**。帯の内側での進み方だけが変わる。

画面 v を経由せず四則演算だけで書ける（tan/atan 版と 3.6e-13 まで一致）:

```
R    = zcJudge_ground / zc_ground(d0)
zc_L = zcJudge_L / (1 + laneConverge * (R - 1) / c_L)
```

**結果（すべて数値検証済み）**:

| 指標 | 修正前 | 修正後 |
|---|---|---|
| 正規化速度比 (Sky/Ground) | 1.932 | **1.0000**（全層・全時刻で厳密に一致） |
| Riser 壁の画面 x のズレ | 最大 27.8% | **0.000%**（壁が厳密に垂直になる） |
| 判定線での幅比 | 0.488 | **1.000**（同じ p なら幅も一致） |
| 最遠端での空中ノーツの厚み | 0.000934 NDC | 0.001804 NDC（**1.93倍**、点滅耐性も向上） |
| 地上ノーツ・拍線 | — | **恒等（誤差 2.8e-14）＝回帰なし** |

地上が恒等になるのは、`layerF=0` では `c_L = laneConverge` となり式から `R` が約分されるため。
**拍線（`NoteBeatLine.shader`）は地上専用なので自動的に無変更。**

残る非対称は「空中レーンは画面上の縦の長さが地上の 0.509 倍」という点のみだが、
これはレーンそのものの長さであり、**その中のノーツ間隔・厚みも同じ 0.509 倍で
一様にスケールする**ので自己整合している（＝体感速度には影響しない）。

### 1.8 【2026-08-06 訂正】§1.7 の初版実装に実害のある不具合があり、tan/atanベースへ差し替えた

§1.7 の初版は X 収束用の zc 比を流用した除算ベースの式
（`zc_L = zcJudge_L / (1 + laneConverge*(R-1)/c_L)`）で実装したが、
**判定線通過の約 0.1 秒後**（`d0` が `aG/cosTheta` 分だけ負に振れた地点、ちょうど
「ノーツが判定線を通っている間」の範囲）**に極（発散点）を持ち**、そこを横切る瞬間に
`depth` が符号反転して画面外へ跳ぶ実害が出た（ユーザー報告: 判定線を通っている間、
奥行きが無限のノーツが追加で表示される。tap は一瞬、band を持つ Slide は帯の分の一定時間）。

原因は、X 収束のブレンド係数 `zc`（`cfg.laneConverge` というアーティスティックな
ノブで制御される、あくまで X 用の便宜的な量）と、実際のスクリーン垂直位置を表す
本物の透視量とを同一視したこと。後者は `StageDerive.cs` の `Psi`/`DepthAt` と同じ
`v(depth) = tan(theta - atan(h/depth)) / tanHalfPhi` で、こちらは tan/atan の二重適用により
角度がいったん有界な範囲へ畳み込まれるため、**同じ入力範囲で極を持たない**
（Python で d0 を -∞ 側まで検証済み: 除算ベース版は d0=-6.25 で符号反転して発散、
tan/atan 版は同じ範囲で単調・有界のまま）。

**修正**: `PlaceNote` の depth 再マップを `VAt`/`DepthFromV`（tan/atan ベース）に差し替え。
地上(`layerF=0`)は分岐で従来どおりの恒等式に落ちるため無コスト。数値的にわずかに重くなるが
（sky系の頂点のみtan/atan）、正しさを優先した。§1.7 の効果（ratio=1.000、Riser壁の
垂直化、地上の恒等性）は新しい実装でも数値検証済みで変わらず成立する。

### 1.9 【2026-08-06 訂正2】帯の外側を再マップ対象から外し忘れ、ほぼ全ノーツが画面全体へ引き伸ばされた

§1.8 で tan/atan ベースに変えた際、**再マップを帯の内側だけに限る条件を入れ忘れていた**。
`pg` は帯の外では [0,1] を外れるため、補間した `v` が地平線（`vHorizon = 0.982`）を越えた時点で
`tan(psi)` の符号が反転し、**判定線の約 2.4 秒より先にある全ノーツが大きな負の `depth` になる**。

負の `depth` はフラグメント側の `depth > _Far` を**通過してしまう**（＝破棄されない）ため、
それらの頂点がカメラ背後に落ちて三角形が画面全体へ引き伸ばされた
（ユーザー報告: slide や tap が一斉に表示されてよくわからなくなる。実際の画面は
Slide のシアンでほぼ全面が覆われていた）。譜面のほぼ全ノーツが該当するので影響は極めて大きい。

**修正**: 再マップは `layerF > 0 && _ZJudge < d0 < _Far` のときだけ行い、**それ以外は従来どおり
`d0` をそのまま使う**。両端は `d0=_ZJudge → depth=_ZJudge` / `d0=_Far → depth=_Far` と
厳密に一致するので継ぎ目は出ない（実測 2e-7 = float32 の精度そのもの）。
帯の内側では `v` は `[vj, vf]` に収まり地平線から十分離れているため、極が存在しない。
併せて地上判定線・最遠端の v 値は uniform で渡すのをやめてシェーダ内で `_ZJudge`/`_Far` から
直接求めるようにした（`pg` が構成上厳密に [0,1] に収まり、`zFar` に `zJudge*200` の
クランプが掛かった場合に `Derived.vFar` とズレる可能性も原理的に消える）。

**検証**: `tau ∈ [-3s, +120s]` の全域で depth が有限・単調・破棄可能であることを確認。
帯の内側の性質（x スキュー 0.000000%、正規化速度比 1.0000、地上の恒等性）はすべて維持。

**教訓（この2回の訂正に共通）**: **検証範囲を「画面に見えている範囲」に限定してはいけない。**
ノーツメッシュは曲全体分の頂点を毎フレーム頂点シェーダに通すので、
`tau` が数十〜数百秒の頂点も必ず評価される。§1.7・§1.8 の検証がどちらも
読み先（1.2 秒）以内しか見ていなかったことが、2回とも見落としの直接の原因だった。

## 2. Ex Tap の巻き込み（`note-spec.md` §6.4 の改訂）

### 2.1 決定

**同時刻に Tap（または Slide 始点）と Ex Tap がセル範囲で交差している場合、
ノーツは両方とも有効なまま、判定は全て Ex Tap とみなす（＝ PERFECT+）。**

現行仕様（rev.5 §6.4）は「同時刻グループはまとめて解決するが、
**ティアはノーツごとに個別に決まる**」だった。今回この後段を覆す。

**適用範囲は「譜面上で交差していれば常に」**（ユーザー選択）。
実行時にその入力が Ex Tap に触れたかどうかは問わない。

### 2.2 「交差」の定義

判定時ではなく**ロード時に静的に決まる**関係として定義する。ノーツ A（Tap または Slide 始点）が
Ex ブーストを受ける条件:

```
∃ Ex Tap E :  |A.time − E.time| < ε          （同時刻、ε = 1e-4 秒）
           ∧  A と E が同じ層              （§6.2「層が違えば無関係」に従う）
           ∧  A と E のセル範囲が交差する
```

セル範囲の交差は A の種別で判定式が異なる:

- **A が Tap / Ex Tap**（離散）: `[cellA, cellA + wA)` と `[cellE, cellE + wE)` の区間交差。
- **A が Slide 始点**（連続）: `[cellF, cellF + width]` と `[cellE, cellE + wE)` の区間交差、
  かつ `|A.layerF − (E の層を 0/1 とした値)| ≤ layerJudgeRadius`。
  離散側の層を連続値に持ち上げて、既存の包含判定と同じ幾何で扱う。

### 2.3 実装方針

`Judge.Prepare(runtimes)` で `chainWindows` を precompute しているのと同じ場所で、
**`NoteRuntime.exBoosted: bool` を precompute する**。判定時は `TierFor()` が
これを見て `JudgeProfile.AllPerfect` と同じ扱いにするだけ。

```
TierFor(kind, absMs, exBoosted):
    if traits.judgeProfile == AllPerfect || exBoosted:  return PerfectPlus
    return JudgeTiers.TierFor(absMs)?.kind
```

- 譜面が変わるたびに再計算が要る（`chainWindows` と同じ扱い。`GameController.Rechart()` は
  既に `judge.Prepare()` を呼んでいるので配線の追加は不要）。
- 探索は現行の縦連判定と同じく O(n²) で問題ない（同時刻グループの走査だけなら実質 O(n)）。

### 2.4 意図的に決めた副作用（把握しておくこと）

1. **Ex Tap 自身が MISS でも、交差する Tap は PERFECT+ になる。**
   「譜面上で交差していれば常に」を選んだ以上これは避けられない。
   譜面作者から見て結果が入力に依存せず予測可能、というのが選択の根拠。
2. **別の指で叩いても Ex 扱いになる。** 巻き込み救済という当初の動機
   （§6.3、Slide 追従中の指の誤爆を救う）を超えて適用される。
   これも 1 と同じトレードオフ。
3. **`chainExempt`（縦連判定の免除）は引き継がない。**
   ブーストされる Tap の実効窓は縦連判定で削られたまま。
   **Why**: 窓の狭さは「1つの入力で連続する2ノーツを解決させない」ための構造で、
   ティアとは別の役割を持つ。ここまで引き継ぐと同時刻に Ex を1枚置くだけで
   縦連判定を回避でき、§6.2 が骨抜きになる（§6.4 が「グループ全体を縦連判定から
   外すことはしない」と明記しているのと同じ理由）。
   **帰結**: 実効窓の内側で叩けば必ず PERFECT+、窓の外なら拾われない、という二値になる。
4. **Flick と Riser には適用しない。** どちらも移動量駆動で「同じ入力イベントで
   まとめて解決される」グループに属さないため（§6.4 が Flick を除外しているのと同じ理由）。

## 3. 新種別 Riser / Diver（層跨ぎノーツ）

### 3.1 確定した設計判断（このセッションでのユーザー選択）

| 論点 | 決定 |
|---|---|
| 正体 | **新 `NoteKind`（Riser = 地上→空中、Diver = 空中→地上）**。既存 Slide の用法整理では済ませない |
| 「Slide の垂直化」の意味 | **時間差 0 で層を移動する＝ワールド空間で垂直な壁**。時間的な広がりを持たない |
| 判定に要求する指の実移動 | **移動量のみ**（軌跡の追従は要求しない） |
| 移動量の閾値 | **空中側に届くまで（layerF で 0.5 以上、NDC v で 0.45 ≒ 11インチ横持ちで約 40mm）** |
| 後続 Slide 始点の緩和 | **Riser の成立を接触点に記録して引き継ぐ（handoff）** |
| データ表現 | **1 Waypoint + `layerTo` フィールド**（同時刻2 Waypoint は採らない） |

### 3.2 動機となる応用フロー

ユーザーが想定している使い方:

```
  地上 Tap   →   同地点で Riser（垂直フリック）  →   空中 Slide
  (t)             (t)                                 (t 以降)
```

1本の指が「地上を叩く → そのまま上へ弾く → 空中のスライドに乗る」という一連の動作になる。
**この流れが成立することが Riser の設計要件**であり、以下の判定設計はここから逆算している。

### 3.3 なぜ「緩和」が構造的に必要か（定量）

現行の `flickDistance` は `U / cells = 0.0725` NDC（0.5セル幅、11インチ横持ちで約 6.4mm）。
一方、地上判定線 `v = -0.75` と空中判定線 `v = +0.15` の間は **0.9 NDC ≒ 80mm**。

`layerF = (v − vGroundJudge) / (vSkyJudge − vGroundJudge)` なので、
**最小フリック（0.0725 NDC）では指は `layerF = 0.081` までしか進まない。**

空中 Slide 始点（`layerF = 1`）の包含判定は `|e.layerF − wp.layerF| ≤ layerJudgeRadius = 0.5`。
`|1 − 0.081| = 0.919 > 0.5` なので、**駆動（EnterEvent）以前に包含判定の時点で落ちる。**

さらに駆動側にも別の壁がある。`EnterEvent` はセル/層/バンドの**離散**境界をまたいだときだけ
発火するが、層の離散境界は `vSplit = -0.1` ＝ `layerF = 0.722`。
つまり **`layerF` が 0.722 を超えないと「空中に入った」イベントは出ない。**

→ **緩めるべきは駆動と包含判定の両方**。この2つは独立した壁で、片方だけ直しても繋がらない。

**採用した解**: 閾値そのものを `layerF ≥ 0.5`（0.45 NDC ≒ 40mm）に引き上げたうえで、
handoff で残りを埋める。閾値を 0.5 にしたことで包含判定（半径 0.5）はちょうど成立するので、
**handoff が救うのは主に駆動側**という役割分担になる。

### 3.4 データモデル

`Waypoint` に **`layerTo: float`** を追加する（既定は `layerF` と同値＝層移動なし）。

```
Note {
  kind        : Tap | ExTap | Slide | Flick | Riser | Diver
  points      : Waypoint[]        // Riser/Diver は length == 1（Tap/Flick と同じ仲間）
  scrollGroup : int
}

Waypoint {
  ...既存...
  layerF  : float     // 始端の層（Riser は 0 付近、Diver は 1 付近が典型）
  layerTo : float     // 終端の層。Riser/Diver 以外は layerF と同値（未使用）
}
```

**Why 同時刻2 Waypoint を採らないか**: 「垂直な壁＝時間的な広がりを持たない」という実態に対し、
時刻の等しい2点は嘘のない表現ではあるが、時間で掛ける既存コードが全て退化ケースの対応を
要求される。実際 `ChartMath.At()` は `b.time == a.time` のとき `k = 0` を返す実装になっており
（`ChartNote.cs:189`）、**同時刻2点だと常に始端の値しか返らない**。
`PushSlideBand`（`steps = max(8, ceil(Δt/0.03))`）も `ChartFormat.ResolveSlideComboPoints` も
Δt > 0 を前提にしている。Riser のジオメトリは「時刻でスイープする帯」ではなく
「1時刻で layerF 方向にスイープする壁」なので、そもそも時間掛けの機構に乗せる意味がない。
`points.Length == 1` に留めれば Tap/Flick と同じ扱いで済み、既存コードに一切手が入らない。

**部分的な層移動を許す**（例: `layerF = 0, layerTo = 0.5`）。`layerF` は全体を通して連続値なので、
ここだけ二値に制限する理由がない。判定の閾値は `|layerTo − layerF|` に比例させる（§3.5）。

**Diver を別 `NoteKind` にするか、Riser の `layerTo < layerF` で表すか**は §3.9 の未決事項。

### 3.5 判定モデル

トレイトは既存の語彙で表現できる（**新しい属性の追加は不要**）:

| kind | startTrigger | sustain | motion | resolution | judgeProfile | chainExempt |
|---|---|---|---|---|---|---|
| Riser / Diver | **Presence** | None | **Flick** | Continuous | Normal | （§3.8） |

すなわち **Flick と同じ駆動機構（`Judge.UpdateFlickPending` 相当）を再利用する**。
Flick との差分は3点だけ:

1. **方向の制約**: Flick は `flickDirection = Any` だが Riser は上向き（Diver は下向き）に限る。
   `note-spec.md` §4.5 で `flickDirection` は `Up`/`Down` を**フィールドだけ予約済み**なので、
   ここでその予約を初めて使うことになる（`StageConfig` には未実装。今回追加する）。
   判定は接触履歴の `Δv` の符号で見る（`Δv > 0` かつ後述の閾値超過で成立）。
2. **閾値**: `flickDistance`（0.0725 NDC、方向不問のユークリッド距離）ではなく、
   **`Δv` 単独で `riserDistance = |layerTo − layerF| × (vSkyJudge − vGroundJudge) × riserReachFrac`**。
   `riserReachFrac` の既定は **1.0**（＝終端の層まで実際に到達させる）。
   現行パラメータ・全層移動（0→1）なら 0.9 NDC。
   **ただし包含判定と噛み合わせるための実効下限として `layerF` で 0.5 に到達すればよい**とする
   （ユーザー選択「空中側に届くまで＝0.45 NDC ≒ 40mm」）。
   → 実装は「`Δv ≥ (0.5 の層距離に相当する v)`」を成立条件とし、
   `riserReachFrac` は実機調整用の設定値として露出する。
3. **包含判定**: 始端の層（`layerF`）側で `|contact.layerF − wp.layerF| ≤ layerJudgeRadius`
   かつ `cellF ∈ [wp.cellF, wp.cellF + wp.width]` を満たす接触のみが対象。
   **移動の起点が枠内にあればよく、終点の位置は問わない**（移動量のみを見るため）。

判定窓・フォールバックは **Flick と完全に同じ**（§4.3 の早い側非対称、§4.4 の
「移動なし＋枠内更新あり → GOOD」）。Flick 用のコードをそのまま通す。

### 3.6 handoff（Riser → 後続 Slide 始点の引き継ぎ）

**`Contact` に層移動の完了を記録し、一定時間だけ「終端の層にいる」とみなす。**

```
Contact {
  ...既存...
  layerHandoffUntil : float   // この時刻まで handoff 有効（songTime 基準の秒）
  layerHandoffTo    : float   // みなす layerF（Riser を成立させたノーツの layerTo）
}
```

- **書き込み**: `Riser`/`Diver` が成立した瞬間、その接触に
  `layerHandoffTo = wp.layerTo`, `layerHandoffUntil = songTime + handoffWindowMs` を書く。
- **読み出し**: 包含判定・`EnterEvent` 生成の両方で、handoff が有効な間は
  接触の `layerF` を `layerHandoffTo` に**読み替える**（実際の `layerF` は上書きしない）。
- **失効**: `handoffWindowMs` 経過、接触の解放（指を離す）、または実際の `layerF` が
  `layerHandoffTo` に自力で到達したとき（到達したら読み替える必要がなくなる）。
- **`handoffWindowMs` の既定は 200ms**（仮値。`flickWindowMs` と同じ「実機で決める」扱い）。

**駆動（EnterEvent）側の扱い**: handoff が成立した瞬間に、
**その接触について終端の層での `EnterEvent` を1回合成して発火する**。
これで「地上の指が空中へ移った」という枠内更新が判定側に届き、
後続 Slide 始点が現行の `OnEnter` 経路のまま解決できる。
`TouchInputManager` が持つ「前フレームの離散状態」も終端層で更新し、
handoff 失効時に二重発火しないようにする。

**Why 合成イベントか**: `Judge` 側に「Slide 始点だけ Presence 駆動に切り替える」分岐を
入れるより、入力層で1回イベントを作るほうが判定側の構造を変えずに済む。
`Judge` は Phase 3 で純粋 C# クラス化してあり、テスト（`JudgeSmokeTest`）も
`EnterEvent` を直接与える形なので、この経路なら handoff 込みのテストも書きやすい。

**誤爆リスク**: handoff 中の指は「空中にいる」とみなされるので、
その 200ms の間に空中の別ノーツを踏む可能性がある。これは §6.3 と同じ問題で、
既存の対処（Ex Tap を置く／譜面レギュレーションで縛る）がそのまま使える。
なお §2 の Ex 巻き込みルール改訂で Ex Tap の救済力が上がっているので、
handoff と組み合わせたときの誤爆耐性は以前より良くなっている。

### 3.7 描画

Riser は**時刻を持つ1枚の垂直な壁**。既存の `PushSlideBand`（時間でスイープ）は使わず、
**`layerF` 方向にスイープする専用の生成関数**を書く。

- 頂点は `(u, y, X(time))` の3成分。`time` は全頂点で同一なので、
  奥行きは頂点シェーダで全頂点同じ値になる＝ワールド空間で判定線に平行な垂直面になる。
- `y = layerF × skyHeight` を `layerF ∈ [layerF, layerTo]` で分割（8〜16分割で十分。
  直線なので曲率による分割数調整は不要）。
- `u` は各 `layerF` で `UAt(cellF)` と `UAt(cellF + width)` の2点。
  **層ごとに `LaneX` の収束補正 `c` が変わる**（`zcFar(layer) / zcFarGround`）ので、
  壁の左右端はワールド空間では厳密な垂直線にならない。これは正しい挙動
  （`muses-stage-ui-design` の「最遠端でワールド x は層ごとに違う」と同じ理由）。
- `nearOf(layerF)` も層ごとに補間する（`NoteGeometry.NearOf` が既にこの形）。
- **`renderQueue` は Notes 帯（3010）と BeatLines（3011）に続けて 3012 を割り当てる**
  （`muses-unity-port-progress` の「3000番台=Stage、3010番台=Notes」の採番規約に従う）。

**視認性の懸念**: 壁は判定線に平行な垂直面なので、カメラから見ると
**真正面を向いた薄い面**になる。奥行き方向の厚みがゼロなので、
`Note.shader` の `ZTest Always` と `renderQueue` 分離が効いていれば消えることはないが、
遠方でどう見えるかは実機で確認が要る（タップノーツで踏んだ「遠方でサブピクセル化して点滅」
の罠と同種の risk がある。ただし壁は画面上で縦に長いので、厚み方向の縮退は起きにくいはず）。

### 3.8 スコア・縦連判定

- **コンボ点は 1**（Tap/Flick と同じ）。`points.Length == 1` なので
  `ChartFormat.ResolveSlideComboPoints` の対象外で、既存のスコア式（§7）がそのまま使える。
- **縦連判定（§6.2）**: Riser は Flick と同じ扱いにする。すなわち
  **早い側だけ免除**（`Judge.Prepare` の Flick 分岐に Riser/Diver を合流させる）。
  **Why**: Flick と同じく移動量駆動で、早押しの概念が Tap と違うため。
- **Ex 巻き込み（§2）の対象外**（§2.4 の 4 のとおり）。

### 3.9 未決事項

1. **Diver を独立した `NoteKind` にするか、Riser の `layerTo < layerF` で表すか。**
   独立させると `flickDirection` を kind から一意に引けて分かりやすい一方、
   トレイト表が2行増える。`layerTo` で表せば表は1行で済み、部分移動との整合も自然。
   → **`layerTo` 方式（kind は `Riser` 1つ）を推す**が、譜面フォーマット・エディタの
   ノーツパレット設計に関わるので、エディタ側を触るときに合わせて決めたい。
2. **`riserReachFrac` / `handoffWindowMs` の実値**（仮 1.0 / 200ms）。
   `flickWindowMs`・`layerJudgeRadius` と同じ「実機で決める」グループ。
3. **Riser を単体（前後に何も無い状態）で置いたときの操作感。**
   40mm のストロークを要求するので、高 BPM の連打には使えない。
   譜面レギュレーションとして最小間隔を決める必要があるかもしれない。
4. **handoff 中の指が空中で「押しっぱなし」になっている状態の扱い。**
   Riser 成立後に指を離さず空中に留まると、handoff 失効後は実 `layerF`（例: 0.6）に戻る。
   このとき空中 Slide の追従（`layerJudgeRadius = 0.5` で `|1 − 0.6| = 0.4` なのでギリギリ通る）は
   続くが、余裕が小さい。**実機で「Riser の後、指が自然にどこで止まるか」を計測してから**
   `layerJudgeRadius` を見直すのがよい。
