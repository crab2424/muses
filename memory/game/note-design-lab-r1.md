今後の進め方（ユーザー要望）・質疑の回答をまとめる。前提の見た目仕様は [note-visual-r1.md](note-visual-r1.md)。

## 1. 方式と環境の判断

### 1.1 3D で並べて比較する方式は適しているか → **適している（条件つき）**
Tap の見た目は「単体のモデル」ではなく**ゲーム視点での写り方**で決まる:
- 画面上の厚みは奥行きで最大約 23 倍変わる（遠方では数 px の線になる）
- 空中面は半透明（背景・地上が透ける）
- 同時刻の横並び・16 分連打などの密度

したがってターンテーブルで 1 個を眺める比較は不適。**Unity の StageConfig・スクロール速度・厚み設定を
そのまま再現したステージ上で、実際にスクロールさせて**比較する形にした。

### 1.2 描画環境 → **three.js（ブラウザ）。Unity は最終確認だけ**
- プロジェクトの出自が three.js 版（`web-prototype/`）で、`Note.shader` 自体が GLSL からの移植。
  逆方向（GLSL → HLSL）の移植経路は実績がある。
- Claude がブラウザで描画結果を直接見て検証・反復できる（Unity の Game ビューは見られない）。
- 保存即反映。Artifact として公開すれば iPad 実機でも見られる。
- 注意: ライティング・PBR は URP と完全一致しない。**形・構造・配色の方向性を決める場**と位置づけ、
  採用案は Unity で最終確認する。

## 5. 質疑（2026-09-29）

### Q1. このページは 120fps で出力され得るか
**される。** 描画は `requestAnimationFrame` 駆動で、ブラウザが画面のリフレッシュレートに同期して呼ぶ。
120Hz の画面で 1 フレームの処理が 8.3ms 以内に収まれば 120fps になる。この Mac のプレビューでは
7 案同時描画で **120 fps を実測**した（ヘッダ右の fps 表示）。
iPad（ProMotion）の Safari は、既定で Web ページの描画更新を 60fps 付近に抑える設定
（設定 → Safari → 詳細 → Feature Flags の「Prefer Page Rendering Updates near 60fps」）が
有効になっている可能性が高い。iPad で見る場合は fps 表示で確認する。
ゲーム本体（Unity）の fps はこのページとは無関係。

### Q2. エンジンに Unity を使っているか
**使っていない。** three.js（WebGL）をブラウザで動かしている。Unity のステージ寸法・カメラ・
ノーツ配置の計算（`StageDerive` / `NotePlacement.hlsl`）を JavaScript に移植して同じ写り方を再現している。
ライティングや材質の見え方は URP と完全には一致しない（§1.2）。

### Q3. 立体描画にコストがかかる場合、平面に見せる / 見えない面（奥・下）の描画省略は可能か
**どちらも可能。** コストの中身を分けて考える:

- **頂点数は実は大きな問題ではない。** キーキャップ／ドームは 1 個約 110 頂点。画面内の Tap が数百個でも
  数万頂点で、iPad の GPU には軽い。
- **本当のコストは描画パイプラインの変更。** 現行はノーツ全部を 1 メッシュ・半透明・`ZWrite Off / ZTest Always`
  で描いている（遠方の Z ファイティング対策）。厚みのある立体は自分自身の面の前後関係が要るので、
  この前提のままだと面の重なり順が崩れる。

対策の選択肢:
1. **見えない面を省く（奥・下）** — カメラは常にノーツの上方・手前にあるので、**底面と奥側の壁は必ずカメラの
   反対を向く**。メッシュから削除でき、頂点は約半分になる。残る面（天面・手前の壁・左右端）は凸形なら
   「壁 → 天面」の順に描くだけで ZTest Always のまま正しく重なる（Opus-B で実証済みの考え方）。
   ただし左右端の壁は、画面中央より左のノーツでは右端、右のノーツでは左端が見えるので残す。
2. **平面に見せる（インポスター）** — 板 1 枚（4 頂点）のまま、フラグメントシェーダで高さの式から法線を計算して
   立体の陰影を付ける。**ドーム（#5）は断面が解析的な楕円なので特に向いている**。現行パイプラインを一切変えずに移植できる。
   弱点は横から見た厚み（手前の壁）が出ないこと。板を手前方向へ壁の高さ分だけ広げ、その部分に壁を描き込めば補える。
3. 立体のまま、ノーツだけ別パス（ZTest 有効）で描く — 最も素直だが Unity 側の改修が最大。

**推奨**: まず 2（インポスター）で #4・#5 を作り直し、本物の立体版と並べて見分けがつくか確認する。
見分けがつかなければ移植コストは現行並みで済む。

## 8. Slide / Riser ラボ（2026-09-29）: `design-lab/note-long/`

ユーザー要望: Slide と Riser（Diver は除外）を Opus 5.5 と Sonnet 5.5 でデモ作成。

- ハーネスは Tap と別。Slide は時間方向の帯、Riser は層方向の壁なので、**Unity と同じく頂点シェーダで配置**する
  （`long.js` の `musePlace()` = `NotePlacement.hlsl` の移植）。ここで作った頂点の積み方・シェーダはほぼそのまま Unity へ持ち込める。
- 出力は `museOut()`（sRGB 変換してから premultiplied）。Unity は Linear 色空間でブレンドする（`m_ActiveColorSpace: 1`）ため、
  three.js で線形のまま premultiply すると半透明の帯が明るすぎた。sRGB 空間で premultiply すると Unity の見え方にかなり近い。
- 起動: `.claude/launch.json` の `design-lab`（vite を design-lab 全体に、port 5181）→ `/note-long/`（Tap は `/note-tap/` でも開ける）。
- 譜面: 直線・重なり / 曲線・層跨ぎ / Riser 連携（地上Tap→Riser→空中Slide、部分移動0→0.5、幅12）/ 密集。

| # | 担当 | 案 | 要点 |
|---|---|---|---|
| 1 | 基準 | 現行 | 帯（地上 α0.30+加算0.22 / 空中 α0.35）＋白線、Riser は縁線＋矢印3つ |
| 2 | Opus 5.5 | レール＋拍刻み / 発射台 | 塗りを薄く・左右端を太いレール、帯の中にコンボ点の刻み（横線）。Riser は足元の発射台バー・行き先の到達線・大矢印1つ |
| 3 | Opus 5.5 | 立体の帯 / ゲート | 低い板（天面は中央ほど明るい、内側の側壁と手前端面は暗色）。凸なので「側壁→天面」の順で ZTest Always のまま可。Riser は柱＋横梁＋足元の台 |
| 4 | Sonnet 5.5 | キーキャップ系 | 暗めのマット板＋太い縁レール＋0.25s 刻みの枕木＋中央の芯線、始点・中継点は不透明のキーキャップ。Riser は太いレール・根元/到達バー・シェブロン列、壁に α0.16 の薄いマット |
| 5 | Sonnet 5.5 | ネオン系 | 淡い加算発光の帯＋ネオンチューブ縁、判定線へ流れる光のパルス。Riser は上向きに流れるシェブロン模様の発光壁（壁の塗りを復活させた理由と代償を unityCost に明記） |

未確認: Sonnet の Slide/Riser はズームビューと密集パターンを自分では見ていない（リードが全体表示の Riser 連携・密集・直線で描画エラーなしを確認）。
