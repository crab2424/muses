# muses ノーツの見た目 — 素材化/形状/色の方針（r1、2026-08-07）

Phase5 の残課題が全て解決したのを受けて着手する「ノーツのモデル化」の設計。
ユーザーから 6 つの論点（形 / 平面・立体 / 色 / 拡張子 / 画像処理 / 種別ごとの扱い）と
参考画像（tap + riser。角を落とした矩形の上にシェブロン、下に赤い角丸ノーツ）が提示された。

**結論を先に**: 画像素材は使わず、**フラグメントシェーダの手続き描画（SDF）** で角丸・輪郭線・
中央線・矢印を出す。平面のままでよく、空中の視認性は**層依存の厚み係数（定数1つ）**で解決する。
以下、各論点をこの結論に至る根拠つきで示す。

---

## 0. 前提: 現状の描画方式（判断の土台）

`Assets/Scripts/Notes/NoteGeometry.cs` / `NoteView.cs` / `Assets/Shaders/Note.shader` /
`Assets/Shaders/Include/NotePlacement.hlsl` を読んで確認した事実:

- **全ノーツが1メッシュ・1マテリアル・1ドローコール**。長尺譜面で約8万頂点、`IndexFormat.UInt32`。
- 頂点にワールド座標は焼かない。`POSITION = (u, y, X(noteTime))` を持たせ、頂点シェーダの
  `PlaceNote` が毎フレーム配置する。`u ∈ [-1,1]` はレーン正規化座標で、ワールド x は
  奥行きに応じたレーン収束補正込みで決まる。
- **テクスチャを一切使っていない**。現在の頂点属性:

  | セマンティクス | 中身 |
  |---|---|
  | `POSITION` | `(u, y, X(t))` |
  | `COLOR` | rgba（alpha は riser-r2 で有効化済み） |
  | `TEXCOORD0` | `(state=表示alpha, near)` |
  | `TEXCOORD1` | `(layerF, side)` — side は厚み方向の符号 |
  | `TEXCOORD2` | `(scrollGroup, -)` |
  | **`TEXCOORD3`** | **未使用（＝ローカルUVを足す余地がある）** |

- ブレンドは `SrcAlpha / OneMinusSrcAlpha`（**加算ではない**）、`ZWrite Off` / `ZTest Always` /
  `Cull Off`。描画順は renderQueue（3010）と**メッシュ内の頂点順＝notes リストの順**だけで決まる。

この構造から、後述の判断がほぼ自動的に決まる。

## 1. 拡張子・画像処理 → **画像を使わない（SDF 手続き描画）**

### 1.1 「大量に読み込むと重い」という前提が成立しない

ノーツは1メッシュ1マテリアルなので、素材を使うとしても**アトラス1枚をロードするだけ**。
枚数は論点にならない。論点になるのは「**遠方でシャープさを保てるか**」の一点。

### 1.2 SVG は選べない

Unity にランタイム SVG は無い。`com.unity.vectorgraphics` はインポート時にテッセレート
またはラスタライズするので、実行時の解像度非依存性は得られない。加えて容量削減のために
未使用パッケージ38個を消した経緯（`memory/editor/editor-ui-redesign.md` §5-3、115.4MB→75MB）
と逆行する。**不採用**。

### 1.3 PNG も分が悪い

このステージは遠近圧縮が極端で、ノーツの画面上の厚みは判定線で `dv=0.069`、最遠部で
`dv=0.003`（**23倍の差**、§3 の実測）。テクスチャだと最遠部でミップ段数を大きく下げることになり、
しかも空中面はカメラに対してほぼ水平（грazing angle）なので異方性フィルタが必須。
それでも「潰れて見える」問題は残る。

### 1.4 SDF（フラグメントシェーダで手続き生成）を採用

- 距離に依らずシャープ。ミップも異方性も要らない。
- 容量ゼロ（アセット追加なし）。
- 角丸・輪郭線・中央線・矢印・シェブロンは**すべて SDF で書ける**。
- 必要なのは `TEXCOORD3` にローカル UV を足すことだけ（Tap 系は矩形内 uv、Slide 帯は横方向のみ）。

**将来「手描きの絵」をどうしても入れたくなったら**、単チャンネル SDF アトラス（PNG 1枚）に
逃がせる。手続き SDF と同じフラグメント側の枠組みに乗るので、後から差し替え可能。

### 1.5 「そのまま流すか、ステージに沿ってアフィン変換すべきか」→ **変換は不要**

形状を `(u, layerF, time)` 空間で定義すれば、`PlaceNote` が層ごとのレーン収束補正まで含めて
正しく変形してくれる。**riser-r2 の矢印がまさにこれで実装済み**（`NoteGeometry.cs`
`PushRiserWall` のコメント参照）。別途アフィン変換を掛ける必要はない。

**ただし重要な制約**: `time` 方向は遠方で極端に潰れる（上記23倍）。したがって

> **視認性に効くディテールは u 方向（レーン横方向）に置くこと。
> time 方向のディテール（角丸の上下、シェブロンの山）は遠方で必ず消える。**

これは §2 と §5 の設計を直接縛る。

## 2. 形 — 隣接ノーツの分離

### 2.1 現状の隙間が消える理由

`NoteGeometry.cs:119-120` で左右に `±0.04` セルの余白を取っているが、これは
**u 空間＝ワールド固定の隙間**なので、遠方でサブピクセルになって消える。
「隣に同じノーツが並ぶと1つの大きいノーツに見える」の直接原因はここ。

### 2.2 本命は「スクリーン空間一定幅の輪郭線」

SDF + `fwidth()` で、**距離に依らず常に約1.5px の縁**を描く。
遠方でも隙間が原理的に保証される。角丸も同じ SDF から同時に得られる。
u 方向の特徴なので §1.5 の制約に抵触しない。**これを分離の主手段にする。**

**確定（2026-08-07）**: 縁の色は**白固定**（ステージが暗色ベースのため、暗い縁より白い縁の
ほうが背景から浮く）。色相ごとに縁色を変える適応処理は**今回は入れない**（装飾はこれ以上
追加しない方針、§2.3・§9-6 も参照）。§7 で述べるとおり、この白い縁が
「帯と同色のマーカー」を視認させる主要な手段も兼ねる。

### 2.3 シェブロン等の装飾は「補助」

参考画像の山形は方向感が出て良いが、time 方向の形なので遠方で消える。
入れてよいが、**分離の主手段にはしない**。手前に来たときの質感向上として扱う。

### 2.4 幾何の隙間は残す

`±0.04` の余白は近距離で効くので残し、輪郭線と二段構えにする。

## 3. 平面 / 立体 → **平面のままでよい。層依存の厚み係数で解決する**

ユーザーの問い「モデルの厚みを従来より増やせば sky に平面で置いても視認性は保たれるか」に
**定量的に答えが出た。答えは YES、しかも補正は定数1つで足りる。**

### 3.1 実測（既定 StageConfig から算出）

`phiDeg=77, yCam=8, thetaDeg=38, vGroundJudge=-0.75, vSkyJudge=0.15, farFrac=0.9` より
`zJudge=3.0999, skyHeight=6.1229, hSky=1.8771, zFar=78.45 (= zJudge×25.3), speed=62.79 u/s`。

2026-08-06 の**奥行き再マップ導入後**（`NotePlacement.hlsl` の `PlaceNote`）、ワールド厚み
`halfThickness = 0.06×zJudge` を持つノーツの画面上の厚み `dv` は:

| 奥行き d0 | 地上 dv | 空中 dv | 空中/地上 |
|---|---|---|---|
| 3.10 (判定線) | 0.06894 | 0.03510 | **0.509** |
| 6.20 | 0.03888 | 0.01980 | **0.509** |
| 15.50 | 0.01274 | 0.00649 | **0.509** |
| 39.22 | 0.00291 | 0.00148 | **0.509** |

**空中ノーツの画面上の厚みは地上のちょうど 0.509 倍で、奥行きに依らず一定。**
比が一定なのは再マップの帰結（両層の画面上の進み具合 p を一致させているので、厚みの比は
そのまま「両層のパネルの画面上の長さの比」= 0.7847/1.5410 = 0.509 に落ちる）。

### 3.2 したがって補正は定数1つ

層依存の厚み係数 **1/0.509 = 1.96** を掛ければ画面上の厚みが完全に一致する。
シェーダ1行（`halfThickness *= lerp(1.0, _SkyThicknessMul, layerF)`）と uniform 1本で済む。
奥行きごとの調整は**不要**（比が一定なので）。

**密度の確認**: 空中の半厚みは `0.06×3.0999×1.96 = 0.365` ワールド単位 = `±5.8ms` 相当。
BPM150 の 1/64（25ms = 1.57 ワールド単位）でも隣と重ならない。**密度的に問題なし。**

### 3.3 留保 — 係数 1.96 が最適とは限らない

厚みを 1.96 倍にすると画面上の**厚み**は地上と一致するが、**ノーツ間隔**は 0.509 倍のまま。
つまり画面上の「厚み ÷ 間隔」は空中だけ地上の 1.96 倍になり、**密な連打では空中のほうが
詰まって見える**。差を全部埋めるのが正解とは限らない。

→ **1.96 を上限、1.0 を下限としてスライダーで実機調整する**。`ThicknessFrac` を
`EditorSettings` へ永続化したスライダーとして残した前例（r13 §7.9）と同じ扱いにする。

**確定（2026-08-07）**: 初期値は **1.96**（＝ §3.2 の理論値、地上と画面上の厚みを完全一致させる
上限）。§7.9 の前例と同様、**恒久設定としてスライダーを残し `EditorSettings` へ永続化**する。
「必要ならユーザー側の設定（プレビュー設定タブ等）にも露出する」— ゲーム側の一般設定に出すか、
開発用の調整タブに留めるかは実装時にユーザーと決める。

### 3.4 立体化は視認性の理由では不要。やるなら別課題

立体化の価値は視認性ではなく**質感**（面ごとの明暗で形が読める、参考画像の見た目）にある。
やる場合のコスト:

- 頂点数が約5倍（8万 → 40万）。
- **半透明なので `ZWrite Off` / `ZTest Always` のままだと自己重なりの描画順が破綻する。**
  現状の「デプステスト無し・メッシュ順で描く」設計と根本的に相性が悪い（このZ設定自体が
  遠距離のZファイティング対策として意図的に入っているもの — `Note.shader` 冒頭のコメント）。

→ **今回は平面で進める。立体化は将来の別テーマとして分離する。**

## 4. 色

### 4.1 ユーザー指定と現状コードの差分

| 種別 | ユーザー指定 | 現状(ゲーム `NoteGeometry.cs`) | 現状(エディタ `ChartEditorApp.cs` `NoteColor`) |
|---|---|---|---|
| Tap | 青（層で変えない） | **層で変わる**: Ground=`#8b5cf6`紫 / Sky=`#ff3ea5`マゼンタ | `#4dcce5` 水色 |
| Ex Tap | 金（黄） | `#ffd54a` ✓ | `#f2cc40` ほぼ同 |
| Flick | 赤 | `#ff4ac8` **マゼンタ寄りピンク** | `#f2734d` オレンジ寄り |
| Slide 帯 | 水色（sky時: 緑） | `#35e8ff` 水色（層共通） | `#66e699` 緑 |
| 中継点(Visible) | tap と同素材・色違い | `白`固定 | — |
| Riser | 緑 | `#4affa0` alpha0.35 ✓ | `#4affa0` ✓ |
| Diver | 紫 | `#c86aff` alpha0.35 ✓ | `#c86aff` ✓ |

### 4.2 確定（2026-08-07、ユーザー判断）

§9 の未決事項として提示した2件はユーザー判断で決着した。「衝突」ではなく**意図的な設計**。

- **sky slide と riser を同色にするのは意図的。** 色の役割を2階層に分けている:
  Tap の色は「操作の役割」、それ以外（Slide/Riser/Diver）の色は追加で**「場所（層）」の役割**を
  兼ねる。Slide は面積が大きく、層をまたいで重なると高さが読みにくくなり得るため、
  **Ground/Sky で色を変える**（Riser/Diver と同じ「層の色」の語彙に揃える）。
  同時に **Ground は不透明、Sky は透明**にする（§5.1 で詳細）。
  → **Tap を層非依存の青に統一する**方針も、この「Tap=操作 / それ以外=場所」の切り分けと
  整合する（Ground/Sky で変えないのは Tap だけでよい）。
- **Flick の赤は判定フィードバックと衝突しない**ことが確定した。§9-3 参照
  （Miss の演出自体を無くす方針になったため）。

### 4.3 色定義が3箇所に分散している（構造的な問題）

`NoteGeometry.cs`（ゲーム）/ `ChartEditorApp.cs` の `NoteColor`（エディタ）/ `StageColors`
（ステージ）に別々のリテラルがあり、上の表のとおり**既にドリフトしている**
（Tap: 紫 vs 水色、Slide: 水色 vs 緑）。

これは `StageConfig` のコード既定値とシーン直列化の二重管理（r13 §7.1 / §10-2）と同じ構図。
**パレット差し替えの前に、共通の `NoteColors` 静的クラスへ集約する。**
`StageColors` と同じ `Muses.Stage` アセンブリに置けばエディタ側からも参照できる
（エディタは既に `StageColors` を `ChartEditorApp.UI.cs:813` で参照している）。

## 5. Slide 帯

### 5.1 確定: Ground は不透明、Sky は透明（2026-08-07、ユーザー判断）

「重なるときに明るさを変化させて区別したいが上限を設けたい」という当初の要望に対し、
ユーザーは Ground/Sky で仕組みを分ける判断をした:

- **Sky（緑）は透明**。当初どおり `SrcAlpha/OneMinusSrcAlpha` の非加算ブレンドにより、
  重なるほど基準色（riser と同じ緑）に飽和し自動で上限がかかる。ここは元の設計のまま活きる。
- **Ground（水色）は不透明**。「直感的にわかりやすい」というのが理由で、ブレンドによる
  明るさ変化の仕組みそのものを使わない判断。

**注意（実装時に確認すること）**: alpha をほぼ 1（例: 0.92〜0.97）にして、
「見た目は不透明」だが**ごく僅かに blend cap の余地を残す**か、文字通り `alpha=1` にするかは
実機で決める。**`alpha=1` にすると 5.3 の重なり順の重要性が跳ね上がる**（後述）。
不透明な帯同士が重なった場合、ブレンドによる「重なっている」手掛かりが一切出ず、
**手前に描かれた帯が奥の帯を完全に隠す**。ほぼ不透明（0.92〜0.97程度）にしておけば、
視覚上は「不透明」に見えつつ、重なった部分だけ僅かに色が変わる手掛かりを残せる
（元々の「明るさを変化させて区別」という要望の趣旨に近い）。**実機で両方試して選ぶ。**

### 5.2 中央線

`PushSlideBand` は既に左右端を `side` で区別して積んでいる（`Emit(p, -1/+1)`）ので、
`TEXCOORD3` に横方向ローカル UV（`side<0 → 0`, `side>0 → 1`）を持たせるだけでよい。
SDF で `v=0.5` に線を引く。

**線の太さはスクリーン空間一定にすること**（`fwidth`）。ワールド固定だと遠方で消える。
u 方向の特徴なので §1.5 の制約はクリアしている。

### 5.3 重要度が上がった: 帯同士の重なり順は譜面のノーツ順に依存する

`ZWrite Off` + `ZTest Always` + メッシュ順描画なので、重なった帯のどちらが上に来るかは
**`notes` リストの順序**で決まる。§5.1 で Ground を不透明にする判断をしたことで、
**この重なり順が「どちらが完全に隠れるか」を直接決めるようになった**（透明なら重なりが
半透明に透けて見えるため多少順序が違っても破綻しにくいが、不透明だとそのまま勝敗が出る）。

`NoteGeometry.Build` のループ順（＝譜面データの `notes` リストの順）を意識する必要がある
（現状は無自覚に入力順のまま）。tick 順にソートしておく、あるいは「後から置いたノーツが
手前に来る」という譜面制作者にとって直感的なルールを明文化しておくのが安全。

## 6. Riser / Diver — 矢印だけにする

**賛成。加えて性能上の根拠がある**: 現状の壁は 12分割 × 2三角の**大面積の半透明**で、
オーバードローが重い（`ZTest Always` なので早期棄却も効かない）。撤去は描画負荷にも効く。

### 6.1 ただし壁が担っていた情報が2つ消える

1. **レーン幅**（`cellF ～ cellF+width`）
2. **始点層 → 終点層のつながり**（`layerF → layerTo`、部分移動もある）

### 6.2 折衷案

- 壁本体（塗り）は撤去する。
- **左右端の細い縦線2本だけ残す**（スクリーン空間一定幅）→ 幅情報を保持。
- **矢印を層方向に3つ程度並べる**（進行方向にサイズまたは濃度のグラデを付ける）
  → つながりと方向感を保持。単発の大矢印より「動き」が読める。
- 面の色が減るぶん、緑/紫の識別は矢印の色に依存する。§4.2 で sky slide と riser を
  意図的に同色にした判断とも整合する（riser 自体が面ではなく矢印になるため、
  「緑い面」同士が並ぶ状況自体が起きにくくなる）。

## 7. tap / ex tap / slide始点 / 中継点(visible) を同素材にする

**方針どおりで、追加実装はほぼ不要。** 現状すでに `QuadThin` で同じ形を積み、色だけ変えている
（`NoteGeometry.cs:121` と `:143`）。SDF 化のときも同じ関数を通るので自動で揃う。

**確定（2026-08-07）**: 中継点マーカーは**始点と同じ色（＝その waypoint の層の slide 色）**にする
方針が決まった。`cSlideMarker = Color.white` 固定をやめ、layerF に応じて Ground/Sky の
slide 色を引くように変更する。

**視認性の担保は「白固定」ではなく「白い輪郭線＋不透明度」で行う**（§6 の輪郭線と整合）:
- §6 で全ノーツに**スクリーン空間一定幅の白い輪郭線**を入れる方針が決まったため、
  マーカーが帯と同色でも**輪郭線1本でマーカーの形（角丸矩形）が帯から浮き出る**。
  帯自体には輪郭線を入れない（またはマーカーより弱くする）ことで差が保たれる。
- **マーカーは alpha を層に依らず常に高く保つ**（帯は Sky で透明・Ground でほぼ不透明だが、
  マーカーは同じ色相のまま常時ほぼ不透明にする）。Sky の透明な帯の上でもマーカーだけは
  くっきり見える。
- 描画順は現状どおり「帯 → マーカー」の順（`NoteGeometry.cs` の実装順）を維持する
  （マーカーが帯より後に積まれることで、輪郭線が帯の上に確実に乗る）。

## 8. 実装順序

依存関係で決まる順。1〜2 と 3以降は別コミットにできる。

1. **色の一元化**（`NoteColors` 共通クラス）＋ パレット差し替え。ゲーム/エディタ両方。
   §4.2 の配色（Tap=層非依存の青、Slide=層依存でRiser/Diverと同色語彙）で確定。
2. **層依存の厚み係数**（シェーダ1行 + uniform 1本 + `EditorSettings` 永続スライダー、初期値1.96）。
   §3 のとおり単独で完結し、効果も大きいので先に入れて実機で係数を確認する。

## 10. 実装完了（2026-08-07）

§8 の実装順序どおり1〜7すべて実装済み。Unity Editorのbatchmode(`-batchmode -nographics -quit`)で
コンパイル確認済み（C#/シェーダとも0エラー）。実機でのPlay確認・見た目調整はまだ。

- **色の一元化**: `Assets/Scripts/Stage/NoteColors.cs`（新規）に集約。ゲーム側(`NoteGeometry.cs`)・
  エディタ側(`ChartEditorApp.cs`の`NoteColor`)の両方から参照するよう書き換え。
  Slideの色は`NoteColors.SlideColor(layerF)`でGround/Skyを連続的に補間する
  （離散切り替えではなく、層を跨ぐSlideに自然に対応）。
- **厚み係数**: `NotePlacement.hlsl`の`PlaceNote`に`_SkyThicknessMul`を追加（`halfThickness`に
  `lerp(1.0, mul, layerF)`を掛けるだけ）。`NoteView.SkyThicknessMul`→`PreviewSystem`→
  `EditorSettings.skyThicknessMul`(既定1.96)→設定モーダルのスライダー(1.0〜1.96)まで配線済み
  （`ThicknessFrac`と同じパターン）。
- **ローカルUV**: `NoteMeshData.localUv`を追加、`PushFn`デリゲートに`localU/localV`を追加。
  モードは`(aSide, localUv.y)`の組で判定: side!=0→タップ形状の角丸+輪郭線SDF、
  side==0かつlocalUv.y==0→Slide帯の端+中央線、side==0かつlocalUv.y<0→Riserの縁線/矢印
  （SDF処理なし、頂点色そのまま）。
- **SDF描画**: `Note.shader`に`RoundedBoxSDF`を追加。`fwidth(dist)`をアンチエイリアス・輪郭幅の
  単位に使うことで、透視変形込みで画面上一定幅の白い輪郭線になる（§2.2の設計どおり）。
  Slide帯は角丸なしで端+中央線のみ（§5.2、時間方向分割の継ぎ目が出ない設計）。
- **Riser/Diver**: 壁の塗りを撤去し、`PushRiserWall`を「左右端の細い縁線(ワールド固定幅で近似、
  §6.2の見送り事項どおり) + 進行方向に3つ並べた矢印」に書き換え。alphaは旧0.35(壁)から
  0.9(縁線)へ引き上げ。
- **エディタ追随**: 色はNoteColorsへの参照に統一。中継点マーカーは白固定から
  `NoteColors.SlideMarkerColor(layerF)`（帯と同色相・常時高alpha）に変更。
  形（角丸・SDF輪郭）はエディタの2Dピアノロールという別の描画文脈のため見送り
  （既存のFillRectOutline等の自前部品はそのまま）。

**次回セッションでやること**: Unity Editorで実機Play確認、§9-1の厚み係数を実際に見て微調整、
Riser縁線のワールド固定幅近似が実機で細すぎ/太すぎないか確認。
