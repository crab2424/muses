## 1. 連続座標の包含判定（Slide / Flick / Riser）

### 1.1 現状（コードで確認した事実）
`Judge.InBand` は
```
|layerF(接触) - layerF(ノーツ)| ≤ layerJudgeRadius(0.5)  ∧  cellF(接触) ∈ [cellF, cellF+width]
```
で、**横方向の余白はゼロ**。Slide が横に動くと指はノーツを追いかける形で数十ms遅れるため、
幅1〜2セルの Slide では遅れた分だけ帯の外に出てしまう。静止している Slide で問題が出にくく、
**移動中だけ厳しい**という報告と一致する。

### 1.2 横方向: 静的余白＋移動方向の時間ずれ許容（ユーザー案「判定を広げる」を採用）
「拾う幅を広げる」（接触点を太らせる）案は Tap と共通の入力モデルに手を入れることになり、
隣接ノーツとの取り合いがゲームシステムごと変わるので採らない（ユーザーの見立てどおり）。

Slide の判定帯を次の2つで広げる。

1. **静的余白 `slideMarginCells`**（左右それぞれ、既定 0.25 セル）。
2. **時間ずれ許容 `slideTrailMs` / `slideLeadMs`**（既定 120ms / 60ms）:
   時刻 t の接触を、帯の t 時点の位置だけでなく **[t − trail, t + lead] の間に帯が通過した横範囲**
   （掃引範囲）と比べる。静止した Slide では範囲が広がらず（＝余計に甘くならない）、
   **速く動く Slide ほど、動いている方向にだけ判定が伸びる**。指の追従遅れという原因に
   直接効く形で、静的余白を大きく取るより隣接ノーツへの影響が小さい。
   - 掃引範囲は [t−trail, t, t+lead] と、その間にある Waypoint の時刻で `ChartMath.At` を取った
     min/max。区間補間が直線なら厳密、easing 区間でも区間端と中点で十分近い。
   - 判定ティアの dt（§2.4 の時間対称判定）はサンプル時刻のまま。帯の位置の許容であって、
     タイミングの許容ではない。

Slide の縦方向（layerF）も同じ掃引を使う（層を跨ぐ Slide で指が遅れる場合も同じ理屈のため）。

### 1.3 縦方向: 「判定線より外側」を判定線上と同一視する（穴の修正）
`layerF = (v − vGroundJudge)/(vSkyJudge − vGroundJudge)` なので、既定値では
- 地上ノーツ(0)の許容: v ∈ [−1.2, −0.3] → 画面下端まで入る
- **空中ノーツ(1)の許容: v ∈ [−0.3, 0.6] → 空中パネルの上部 v∈(0.6, 1.0]（画面上端から約20%）が判定外**

Tap は離散パネル（v > vSplit なら空中）なので空中パネル全体で取れる。つまり
**同じ空中パネルでも、上の方を押すと Tap は取れるのに Slide/Flick/Riser は取れない**状態だった。

修正: 包含判定では接触の layerF を **[0, 1] にクランプしてから**比べる。
「各層の判定線より画面の外側」は判定線上と同じ扱いになり、空中パネル上部の穴が消える。
中間層（layerF≈0.5）の Slide は画面全体で取れるようになるが、元々 radius 0.5 で
判定線間のほぼ全域を許容しているので実害はない。

**残る差（今回は変えない）**: 層の境目は Tap が vSplit(−0.1)、連続判定が layerF 0.5（v=−0.3）で
0.2 NDC ずれている。揃えるには layerF の写像を折れ線にする必要があり、中間層 Slide の見た目の位置
とのずれ・Riser の閾値にも波及するので見送る。実機で問題が出たら `layerJudgeRadius` を上げる
（0.6 で地上側は v=−0.21 まで）のが第一手。

### 1.4 Flick / Riser
- Flick の縦枠は **Slide とまったく同じ関数**（`InBand`）なので広さは同じ。§1.3 の修正も同時に効く。
- Riser に横余白 **`riserMarginCells`（既定 0.5 セル）** を追加。Riser は縦に大きく振る操作で
  横位置の精度が落ちやすいため Slide より広めにする。
- Flick にも同じ口 **`flickMarginCells`（既定 0 = 現状維持）** を用意する（要望外なので既定は変えない）。
- 時間ずれ許容は Flick / Riser には入れない（1点しか時刻を持たず、掃引範囲が生じないため）。

### 1.5 パラメータ（`StageConfig`、実機で調整）
| 名前 | 既定 | 意味 |
|---|---|---|
| `slideMarginCells` | 0.25 | Slide帯の左右の静的余白（セル） |
| `slideTrailMs` | 120 | 指の遅れの許容（帯が過去この時間に居た範囲も当たり） |
| `slideLeadMs` | 60 | 先回りの許容（帯がこの時間後に来る範囲も当たり） |
| `flickMarginCells` | 0 | Flickの左右余白 |
| `riserMarginCells` | 0.5 | Riserの左右余白 |

`StageConfig` はシーンに直列化されているため、**新フィールドにはフィールド初期化子を付ける**
（付けないと既存シーンでは 0 で読み込まれる）。

## 2. Slide 始点判定の廃止（ユーザー判断、note-spec rev.8 相当）

### 2.1 現状
始点は Tap と同じ「枠内更新」（新規接触、またはセル/バンド境界をまたぐ移動）で駆動していた
（note-spec §0.2）。見た目には Tap 型の頭が無い（始点 marker は既定 None）ため分かりにくく、さらに
**前の Slide の終点と次の Slide の始点が同じ位置だと、指を動かさない限り始点が MISS になる**。

### 2.2 変更
**始点も他のコンボ点と同じ「占有駆動・時間対称」の判定にする**（§2.4 と同じ規則）。
- 始点時刻 t0 の ±100ms に帯（§1.2 の余白込み）の中に接触があれば成立。押しっぱなしで入ってきてもよい。
- Tap 的な始点が欲しい譜面は、譜面側で同時刻に Tap を重ねる。
- 始点の `marker` は従来どおり「Tap型マーカーを重ねて描くか」の見た目指定のみ。

### 2.3 仕様上の帰結
- 縦連判定（中点分割、§6.2）の対象集合 T から Slide 始点を外す（占有駆動には窓の中点分割が意味を持たない）。
- Ex Tap 巻き込み（§6.4）の対象から Slide 始点を外す（駆動が枠内更新でなくなったため。Flick が対象外なのと同じ理由）。
- 同時刻まとめ解決（§6.4）の対象から外れる（同上）。
- Riser の handoff（§4.6.4）は、合成 EnterEvent ではなく**接触の実効 layerF の読み替え**で後続 Slide 始点に効く
  （`InBand` が既に `EffectiveLayerF` を読んでいるので追加実装は不要）。

### 2.4 ついでに直す既存不具合: スコアの分母 N
`N` を `comboTimes.Count` で数えていたが、`comboTimes` は始点を含まない（始点は別経路で判定していた）。
**始点の判定がスコアに入るのに N に数えられていなかった**ので、全 PERFECT+ で 1,010,000 を超えていた。
`ChartMath.ComboPointCount(note)`（Slide は comboTimes.Count+1）に一本化し、
GameController / PreviewSystem / ChartValidator の3か所をこれに揃える。

### 2.5 ついでに直す: コンボ点の確定遅れ（note-spec §9-4）
コンボ点は `t_p + 100ms` まで待って確定していた（遅れて掴んだ場合も救うため）。
判定演出（§3）を付けると 100ms 遅れが目に見えるので、**早期確定**を入れる:
時刻 now（≥ t_p）で、既知の占有サンプルの最良 |diff| が `now − t_p` 以下なら、
**以降のサンプルがそれより良くなることはない**ので、その場で確定してよい（結果は待った場合と完全に同じ）。
押しっぱなしなら t_p 直後のフレームで確定する。遅れて掴んだときだけ従来どおり待つ。

## 3. 判定表示とコンボ

- **判定名**: ノーツの判定線上（セル範囲の中央）の少し上にポップアップし、上へ流れながら0.45秒で消える。
  - 色: PERFECT+ = 金 `#ffd54a`、PERFECT = 橙 `#ff9f43`、GOOD = 緑 `#4ade80`、MISS = 灰 `#9ca3af`。
    背景が明るい（`#a0b298`）ので暗い縁取りを付ける。
  - Slide のコンボ点は毎秒4〜8回出るので、**同じ層で近い位置（0.75セル以内）に表示中のものがあれば
    それを使い回す**（積み重ならない）。
  - ラベルはプール（UI Toolkit `Label`、最大24）。位置は `translate` で動かす（レイアウト再計算を起こさない）。
- **コンボ**: 層の境目（`vSplit`）の画面中央。数字を大きく、下に小さく "COMBO"。
  半透明（ノーツの流れを隠さない）、増えた瞬間に小さく拡大して戻る。コンボ0（開始直後・MISS直後）は非表示。
- 既存の左上 HUD（時刻・fps・音源誤差のデバッグ表示）はそのまま残す。

## 4. ヒット演出（PERFECT 以上）

「光の輪＋火花」。判定線上のノーツ位置に:
- **光**: 横長の柔らかいグロー（ノーツ幅に合わせる）が一瞬強く光って消える。
- **輪**: 楕円のリングが広がりながら薄くなる（縦を潰して奥行きのある床に乗っている感じにする）。
- **火花**: 6個（PERFECT+は8個）の小さな光点が上向きに散り、少し落ちながら消える。
- PERFECT+ は金、PERFECT は白寄りの水色。PERFECT+ は一回り大きい。
- **Slide のコンボ点は軽量版**（小さいグローのみ）。毎秒8回、火花まで出すとうるさいため。
- GOOD / MISS は従来の判定線上の矩形フラッシュのまま（note-visual-r1 §9-3 の方針どおり MISS に派手な演出はしない）。

**実装方式**: UI Toolkit のオーバーレイ（`StageOverlay`、判定線と同じ座標系）に、
実行時生成したテクスチャ（放射グラデーション・リング・点、各64px）を貼った `VisualElement` をプールして
`translate / scale / opacity / tint` だけ毎フレーム更新する。
- Bloom は軽量化（perf-r1【A】）で切ったため、光の柔らかさはテクスチャのグラデーションで出す。
- Painter2D で描くと毎フレームのパス分割が CPU に乗る（火花・リングは細かい）。テクスチャ貼りなら
  要素数 ×（位置・色の書き換え）だけで済む。同時に出る演出は多くても十数個。
- UI Toolkit は通常アルファ合成のみ（加算不可）。判定線付近の背景は暗い床なので問題ない。

## 5. ノーツの見た目

### 5.1 端の形（ユーザー指定）
基本は長方形のまま、左右の端だけ変える（`Note.shader` の SDF）。
- **Tap / Ex Tap**: `( )` — 左右端を半円に（カプセル形）。
- **Flick**: `< >` — 左右端を尖らせる（横向きの六角形）。尖りの深さは厚みの半分×1.2 程度。
- Slide の中継点マーカーは従来の角丸矩形のまま（始点判定が無くなったので、Tap と同じ形にすると
  「叩く必要がある」と誤読される）。
- 種別タグ `localUv.y` を拡張: 1=Tap系(カプセル) / 2=Flick(尖り) / 3=中継点マーカー(角丸矩形)。

### 5.2 薄い立体感（「間近で止めて見たら厚みがあるな」程度）
- 厚み方向に上（奥側）を僅かに明るく、下（手前側）を僅かに暗くするグラデーション（±8%）。
- 上端のすぐ内側に細いハイライト、下端に細い影（面の縁が立っているように見える）。
- どちらも画面上の厚みが数px以下（遠方）では自動で消える（輪郭線と同じ軸別の px 換算を使う）。

### 5.3 Slide 帯: 重なるほど明るく、上限約4枚
- **地上 Slide**: 不透明（alpha 0.94）をやめ、**暗めの半透明**にして、**重なった枚数ぶん等間隔で明るくなる**
  加算寄りの合成にする。上限は**ステンシルで厳密に4枚**（5枚目以降はそのピクセルに描かない）。
  - 合成: premultiplied（`Blend One OneMinusSrcAlpha`）で「通常合成 α=0.30 ＋ 加算 0.22×色」。
    1枚ごとの増分がほぼ一定になり、通常合成だけの場合（2枚目以降の変化が急に小さくなる）より段が読める。
  - ステンシル: `Ref 4 / Comp Greater / Pass IncrSat`（そのピクセルの帯の枚数が4未満なら描いて+1）。
- **空中 Slide**: 従来どおり α=0.35 の通常合成（重なると自然に飽和する）。空中面は地上の遠方と画面上で重なるので、
  ステンシルを共有すると地上の帯の枚数で空中の帯が消えることがあるため、**空中側はステンシルを使わない**。
- **帯とそれ以外を別サブメッシュに分ける**（ステンシル・合成方式はマテリアル単位でしか変えられないため）:
  - sub0 = 地上寄りの帯（三角形の layerF 平均 < 0.5）: キュー 3008、ステンシル＋加算寄り
  - sub1 = 空中寄りの帯: キュー 3009、通常合成
  - sub2 = それ以外（Tap / Flick / マーカー / Riser）: キュー 3010（従来）
  頂点配列は共有なので、Judge が書く頂点範囲（alpha・食べる/通り過ぎる）はそのまま使える。
  層を跨ぐ Slide は途中で合成方式が切り替わるが、色は元々 layerF で連続補間している。
- **重なり順の変化**: マーカー・Tap は全ての帯より後に描かれるようになる（従来は同じ Slide の帯の直後）。
  「後の Slide の帯がマーカーを隠す」ことが無くなるので改善方向。
- 3D プレビュー（譜面エディタ）の RenderTexture は深度16bit（ステンシル無し）だったので 24bit にする。

### 5.4 ついでに直す: Visible 中継点マーカーが判定線で食べられずに浮く（保留課題）
マーカーの頂点範囲を、そのコンボ点の区間（`comboSegmentVertexRanges[i]`）と同じフラグで制御する。
`NoteRuntime.comboMarkerVertexRanges[i]` を追加し、`SetSlideSegmentEatable` が両方を書く。
シェーダはタップ系の分岐でも `slideEatable` なら判定線より手前を削る。始点のマーカーは区間0に属させる。

## 6. 背景ビジュアル（将来、見積もりのみ）

### 6.1 どこが見えるか
背景（クリア色 `#a0b298`）が実際に見えるのは**ステージ最遠端より上**と**左右の余白**だけ。
地上面は不透明（groundFillAlpha=1）で画面下半分を覆い、空中面は α0.2 で遠方を覆う。
→ 動く背景の大部分はステージに隠れる。**全画面で重い処理をするのは割に合わない**。

### 6.2 案とコスト（iPad、2360×1640×renderScale 0.8 ≒ 250万px、120fps）
| 案 | 描画コスト | 備考 |
|---|---|---|
| A. 縦グラデーション（全画面1枚） | ほぼ0（頂点4、フラグメント1命令） | 既存のクリア色を置き換えるだけ |
| B. A＋ゆっくり流れる手続きパターン（ノイズ雲・光の帯） | 中: 全画面×ノイズ数オクターブ。250万px×120fps でタイル型GPUでも数%〜10%程度 | **見えない部分（ステージの裏）も計算する**のが無駄。ステンシルかキューで「ステージより後に、ステージが無い所だけ」描けば半分以下 |
| C. 曲に反応（低音で明滅、`AudioSource.GetSpectrumData`） | CPU: 1024点FFT取得で約0.05ms/フレーム。GPU: uniform を1〜2本足すだけ | B と組み合わせると効果大。オーディオの読み出しは30Hz程度に間引いてよい |
| D. パーティクル（漂う光の粒） | 低〜中: 粒数×小さい四角。200粒程度なら無視できる | 透明の重ね描きなので、大きい粒を多数置くと急に重くなる |
| E. 動画背景 | 高: デコード（HW支援あり）＋全画面テクスチャ。容量も数十MB増 | 軽量化（105MB）と逆行。非推奨 |

### 6.3 推奨
**A → A+C → B（領域限定）** の順。A と C は実質ゼロコストで「曲に合わせて空が脈打つ」まで行ける。
B を入れるなら「ステージより後に描き、深度/ステンシルでステージの無い所だけ」にして、
Profiler の GPU 時間で 0.5ms 以内を目安にする（現状 1フレーム8.3ms のうち実処理 約2.8ms、perf-r1 §14）。
なお 120fps 固定をやめる（perf-r1【J】）と背景に使える余裕は倍になる。
